# M9. Структура проекта

**Статус:** ✅ fixed
**Дата фиксации:** 2026-10-25
**Связанные:** M1 (адресация), M2 (связи), M3 (версии), M10 (связь с KB), M13 (генерация), M15 (Quick Capture), M16 (кросс-проектный), M17 (портфель)
**Расширяет:** M3 (версионирование) — см. ADR-022

---

## 1. Контекст

**Какую задачу решаем.** Контент проекта известен (CONTENT_INVENTORY v5).
Нужно решить: **где именно** он будет лежать. Не «что хранить», а
«как разложить по полочкам».

**Ключевые требования (из UX):**
- Пользователь не думает о структуре — система сама раскладывает.
- Артефакты должны быть **находимы** (M7-full, M16).
- Структура должна быть **расширяемой** (новые проекты, новые артефакты).
- Проектные артефакты **не версионируются** как KB-файлы (M3).

**Аналогия из 1С.** Это как **спроектировать справочники и документы**
перед настройкой учёта. Контент известен, но надо решить:
- какие реквизиты в «карточке проекта» (meta.yaml);
- как называются проекты (project_id);
- как группировать артефакты (по этапам / по типам);
- где хранить «единые» файлы (change log, реестр проблем, паспорт);
- как отмечать «условные» артефакты (миграции не было).

### 3.2. meta.yaml — карточка проекта

```yaml
# meta.yaml — карточка проекта
project_id: aquaservice
project_name: "ООО АкваСервис"
client: "ООО АкваСервис"

config:
  - unf
config_version: "3.0.14"

status: active          # active | paused | closed | archived
stage: 02_implementation # текущий этап
health: green           # green | yellow | red

created: 2026-10-20
updated: 2026-10-25

team:
  - { role: analyst, name: "Иванов И.И." }
  - { role: implementer, name: "Петров П.П." }
  - { role: pm, name: "Сидоров С.С." }

conditional_artifacts:
  migration: not_applicable
  escalation: applicable
  glossary: applicable

kb_links:               # для M10
  - unf/sales/reference
  - unf/warehouse/practical
```

**Что важно:**

- `stage` — текущий этап (для дашборда и M9-навигации).
- `conditional_artifacts` — какие условные артефакты применимы.
- `health` — светофор для директора.
- `kb_links` — связь с KB (M10).

**Чего НЕТ:** бюджет, маржинальность, риски-каунтер. Это вычисляется
из артефактов (M16/M17), не хранится в meta.yaml. Иначе meta.yaml
станет «второй бухгалтерией», которую нужно синхронизировать.

### 3.3. project_id

**Правило:** slug из названия клиента (`aquaservice`, `romashka`).

**Если два проекта с одинаковым названием:** суффикс (`aquaservice-2`).

**Если клиент переименовался:** `project_id` **не меняется** (как «Код»
в 1С — стабильный идентификатор).

**Генерация:** при создании проекта (задача реализации M9). Пользователь
может переопределить, но по умолчанию — slug.

### 3.4. Версионирование артефактов проекта (гибрид — расширение M3)

**⚠️ Внимание:** это **расширение M3**, а не новое решение. См. ADR-022.

**M3 фиксировал:** «Проектные артефакты — другая модель: `status: draft →
approved → superseded`, без номеров версий».

**M9 расширяет:** для артефактов, которые **пересматриваются** (ТЗ,
требования, модель TO-BE), нужен и номер пересмотра (`vN`).

| Атрибут ↕▾ | Что означает ↕▾ | Пример ↕▾ |
|---|---|---|
| −`status` | Жизненный цикл документа | `draft` → `approved` → `superseded` |
| `version` | Номер значимого пересмотра | `v1`, `v2` |
⚙

**Когда создаётся новая версия:**

- ТЗ утверждено (`approved`), клиент просит изменить → новая версия (`v2`),
старая — `status: superseded`.
- Протокол встречи — **не версионируется** (это факт, а не документ).
- Чек-лист — **не версионируется** (можно перегенерировать).
- Заметки — **не версионируются** (это сырьё).

**Какие артефакты версионируются:**

| Версионируются (vN) ↕▾ | Не версионируются ↕▾ |
|---|---|
| −ТЗ на доработку (`tz-modifications.md`) | Протоколы встреч (`meetings/`) |
| Требования (`requirements.md`) | Чек-листы (`checklist.md`, `setup-checklist.md`) |
| Модель TO-BE (`to-be.md`) | Заметки (`notes.md`) |
| Карта соответствия (`mapping.md`) | Реестры (`registry-*`, `issues-log`) |
| Gap-анализ (`gap.md`) | Факты (`system-passport`) |
⚙

**Аналогия из 1С:** это как **«Версии объекта»** в справочнике. Каждая
версия имеет статус (актуальная / устаревшая) и номер. Оба атрибута.

### 3.5. Дашборд проекта

**Не хранится как файл.** Генерируется по запросу из `meta.yaml` +
артефактов.

**Что в дашборде:**

- Статус этапов (какие пройдены, какие в работе).
- Открытые риски (топ-5 из `registry-risks.md`).
- Открытые проблемы (из `issues-log.md`).
- Последние решения (из `registry-decisions.md`).
- Health (из `meta.yaml`).
- Ссылки на ключевые артефакты.

**Если нужен кэш:** `.cache/dashboard-{project_id}.md` (gitignored).

**Аналогия из 1С:** это как **«Пульс бизнеса»** — отчёт, а не документ.
Не хранится, строится по запросу.

### 3.6. Условные артефакты

**Отмечаются в `meta.yaml`:**

```
conditional_artifacts:
  migration: not_applicable     # миграции не было
  escalation: applicable        # крупный проект, эскалация нужна
  glossary: applicable          # богатая терминология
```

**Файл не создаётся, если `not_applicable`.** Если позже станет
`applicable` — файл создаётся при первом обращении.

### 3.7. Архивация проекта

**Не переносить в `_archive/`.** Проект остаётся на месте,
`status: archived` в `meta.yaml`.

**M16/M17 по умолчанию не включают архивные проекты** (фильтр
`status != archived`). Если нужен архивный — явный фильтр.

**Аналогия из 1С:** это как **«Пометить на удаление»** — объект остаётся
в базе, но не участвует в работе.

### 3.8. Использование артефактов на других этапах

**Правило:** артефакт «живёт» в папке этапа, где создан, но может
**использоваться (быть прочитан)** на других этапах.

**Пример:** `stakeholders.md` создан на этапе 1 (`00_questionnaire/`),
но используется на этапе 3 для коммуникации. Он **не копируется** —
на него ссылаются через M10 или M7-full.

**Почему не копировать:** копия устареет. Ссылка — всегда актуальна.

**Аналогия из 1С:** это как **«Ввести на основании»** — новый документ
ссылается на старый, но не копирует его данные.

### 3.9. registry-decisions — где создаётся

**Создаётся на этапе 2** (первое проектное решение), но **живёт в корне**
(сквозной артефакт).

**Почему в корне:** он обновляется на всех этапах (этап 3, 4, 5).
Если бы он лежал в `01_design/`, при переходе на этап 3 пришлось бы
переносить.

**Аналогия из 1С:** это как **«Журнал документов»** — создаётся при
первом документе, но живёт отдельно от папок с документами.

### 3.10. Инициализация проекта

**M9 не описывает процесс инициализации** (кто создаёт `meta.yaml`,
как создаются папки). Это **задача реализации**.

**M9 определяет:**

- Что должно быть создано (структура + meta.yaml-шаблон).
- Где это лежит.
- Какие поля в meta.yaml.

**Реализация создаёт это при «новом проекте».** Как «Новый документ»
в 1С — пустая форма, которую заполняет пользователь.

### 3.11. Связь M9 ↔ M13

**M9 определяет структуру** (где что лежит). **M13 создаёт файлы**
в этой структуре.

M13 не решает «куда» — он использует шаблон структуры от M9.

**Аналогия из 1С:** «Справочник Номенклатура» (структура) и «Загрузка
данных» (создание элементов). Загрузка не решает, какие реквизиты —
она заполняет существующие.

## 4. Почему так (обоснование)

### Почему по этапам + сквозные в корне

**Альтернатива «только по этапам»:** сквозные артефакты (реестр рисков,
change log) непонятно куда. Они не принадлежат одному этапу.

**Альтернатива «только по типам»:** не видно, на каком этапе что
создаётся. Теряется контекст проекта.

**По этапам + сквозные:** видно и этап, и сквозные артефакты.
Как в 1С: документы — по журналам, а общие справочники — отдельно.

### Почему гибрид status + vN (расширение M3)

**M3 фиксировал только status:** практика показала, что для
пересматриваемых артефактов (ТЗ, требования) нужен и номер.

**M9 расширяет:** гибрид. Не отменяет M3, а дополняет.

**Почему не переписывать M3:** M3 уже fixed. Расширение — через ADR-022.

### Почему дашборд генерируется

**Альтернатива «отдельный файл»:** забыл обновить — устарел.

**Генерируется:** всегда актуален. Как отчёт в 1С.

### Почему условные артефакты в meta.yaml

**Альтернатива «файл с пометкой»:** лишний файл. Загрязняет структуру.

**Запись в meta.yaml:** компактно. Видно, что «мы проверили и решили,
что не нужно».

### Почему архивация через status, а не перенос

**Альтернатива «перенос в _archive/»:** ломает ссылки. M16/M17 должны
знать, где искать.

**status: archived:** ссылки работают, M16/M17 фильтруют по статусу.
Как «Пометка на удаление» в 1С.

### Почему артефакт не копируется на другой этап

**Альтернатива «копировать»:** копия устареет. Две версии одного факта.

**Ссылаться через M10/M7-full:** всегда актуально. Как «Ввести на
основании» в 1С.

## 5. Что отвергли (альтернативы)

| Альтернатива ↕▾ | Почему отвергли ↕▾ |
|---|---|
| −Только по этапам (без сквозных в корне) | Сквозные артефакты непонятно куда |
| Только по типам | Не видно этапа |
| Только status (без vN) | Не видно, сколько раз пересматривали (M3 расширен) |
| Только vN (без status) | Не видно жизненного цикла |
| Дашборд — отдельный файл | Забыл обновить — устарел |
| Условные артефакты — файл с пометкой | Лишний файл |
| Архивация — перенос в `_archive/` | Ломает ссылки |
| meta.yaml с бюджетом и маржинальностью | «Вторая бухгалтерия», нужно синхронизировать |
| Копировать артефакт на другой этап | Копия устареет |
| M9 описывает инициализацию | Это задача реализации, не спецификации |
⚙

## 6. Стресс-тест (edge cases)

### E1. Проект закрыт

**Поведение:** `status: closed`, файлы остаются на месте, M16/M17
фильтруют.

### E2. Клиент вернулся через год

**Поведение:** `status: active`, stage восстанавливается из последнего
этапа.

### E3. Артефакт создан на этапе 1, нужен на этапе 3

**Поведение:** живёт в папке этапа 1, ссылка через M10 или M7-full.
**Не копируется.**

### E4. Условный артефакт стал применимым

**Поведение:** `conditional_artifacts.migration: applicable`, файл
создаётся при первом обращении.

### E5. Дашборд при отсутствии meta.yaml

**Поведение:** не генерируется, показывается «Проект не инициализирован».

### E6. Два проекта с одинаковым названием

**Поведение:** `project_id` с суффиксом (`aquaservice-2`).

### E7. KB-файл, на который ссылается проект, обновился

**Поведение:** M10 + M12: флаг `requires-review` в проекте.

### E8. Проект использует несколько конфигураций

**Поведение:** `meta.yaml: config: [unf, zup]`.

### E9. Артефакт approved, клиент просит изменения

**Поведение:** `status: superseded`, новый файл `v2`.

### E10. Реестр проблем пуст

**Поведение:** файл `issues-log.md` не создаётся, пока нет первой
проблемы.

### E11. Проект удалён (не архивирован, а именно удалён)

**Поведение:** это **не штатная операция**. Проект не удаляется,
только архивируется (`status: archived`). Если нужно «удалить» —
это ручное решение с бэкапом.

### E12. Проект переименован (клиент сменил название)

**Поведение:** `project_id` не меняется, меняется `project_name` и
`client`. Ссылки работают.

### E13. Артефакт версионируется, но клиент не согласовал

**Поведение:** `status: draft`, `version: v2`. Клиент не согласовал —
v2 не становится `approved`.

### E14. Протокол встречи — нужна ли версия?

**Поведение:** **нет**. Протокол — это факт («что было сказано»).
Если встреча пересмотрена — новый протокол с новой датой.

## 8. Связанные механизмы

- **M1 (адресация):** проектные артефакты адресуются по пути

- **M15 (Quick Capture):** заметки попадают в `00_questionnaire/notes.md`.

- **M17 (портфель):** использует `meta.yaml` (статус, health, stage).

## ADR-021. Структура проекта (M9)

**Дата:** 2026-10-25
**Статус:** accepted

**Контекст:** контент проекта известен (CONTENT_INVENTORY v5). Нужно
решить, **где именно** он будет лежать.

**Решение:** структура проекта.

### 1. Группировка — по этапам + сквозные в корне

```
01_projects/{project_id}/
├── meta.yaml
├── change-log.md              ← сквозной
├── issues-log.md              ← сквозной
├── system-passport.md         ← сквозной
├── registry-risks.md          ← сквозной
├── registry-decisions.md      ← сквозной
├── 00_questionnaire/          ← этап 1
├── 01_design/                 ← этап 2
├── 02_implementation/         ← этап 3
├── 03_launch/                 ← этап 4
└── 04_support/                ← этап 5
```

### 2. meta.yaml — карточка проекта

Поля: `project_id`, `project_name`, `client`, `config`, `config_version`,
`status`, `stage`, `health`, `created`, `updated`, `team`,
`conditional_artifacts`, `kb_links`.

**Чего НЕТ:** бюджет, маржинальность (вычисляется из артефактов M17).

### 3. project_id — slug из названия клиента

`aquaservice`, `romashka`. При конфликте — суффикс (`aquaservice-2`).
Не меняется при переименовании клиента.

### 4. Версионирование — гибрид status + vN

**⚠️ Расширение M3** (см. ADR-022).

- `status`: `draft → approved → superseded` (жизненный цикл).
- `vN`: номер значимого пересмотра — **только для пересматриваемых**
артефактов (ТЗ, требования, TO-BE, карта, gap).
- Протоколы, чек-листы, заметки — **не версионируются**.

### 5. Дашборд — генерируется, не хранится

Из `meta.yaml` + артефактов по запросу. Если кэш — `.cache/` (gitignored).

### 6. Условные артефакты — запись в meta.yaml

`conditional_artifacts: { migration: not_applicable }`. Файл не создаётся,
если не применимо.

### 7. Архивация — через status, не перенос

`status: archived`. M16/M17 фильтруют по статусу. Не переносить
в `_archive/` (ломает ссылки).

### 8. Артефакт на этапе — не копируется

Живёт там, где создан. Используется на других этапах через M10/M7-full.

### 9. Инициализация — задача реализации

M9 определяет «что» (структура, meta.yaml). Реализация создаёт
при «новом проекте».

**Альтернативы:**

- Только по этапам (без сквозных в корне) — отвергнуто.
- Только по типам — отвергнуто.
- Только status (без vN) — отвергнуто (расширение M3).
- Дашборд — отдельный файл — отвергнуто.
- Условные артефакты — файл с пометкой — отвергнуто.

## ADR-022. Расширение версионирования проектных артефактов (M3 → M9)

**Дата:** 2026-10-25
**Статус:** accepted

**Контекст:** M3 (ADR-009) зафиксировал: «Проектные артефакты — другая
модель: `status: draft → approved → superseded`, без номеров версий
(«утверждено клиентом» — не «версия 2»)».

M9 (ADR-021) вводит гибрид: `status` + `vN` для проектных артефактов.

**Это прямое противоречие.** M9 расширяет M3, но это не было явно
зафиксировано.

**Решение:** M9 **расширяет** M3, а не отменяет его.

**Что расширяется:**

- M3: для проектных артефактов — только `status`.
- M9: для **пересматриваемых** артефактов (ТЗ, требования, TO-BE,
карта, gap) — `status` + `vN`.
- Для **непересматриваемых** (протоколы, чек-листы, заметки) —
только `status`, без `vN`.

**Почему это расширение, а не отмена:**

- M3 остаётся в силе для KB-файлов (v1, v2, v3 + `_versions/`).
- M3 остаётся в силе для **базовой** модели проектных артефактов
(`status: draft → approved → superseded`).
- M9 добавляет `vN` **только** для пересматриваемых артефактов.

**Альтернативы:**

- Переписать M3 — отвергнуто: M3 уже fixed, переписывать нельзя.
- Оставить M9 без vN — отвергнуто: практика показала, что для ТЗ
нужен номер пересмотра.
- Ввести vN для всех проектных артефактов — отвергнуто: протоколы
и чек-листы не пересматриваются.

**Следствия:**

- M3 остаётся fixed, но с пометкой «расширено в M9» (в описании).
- M9 — fixed с пометкой «расширяет M3».
- При реализации: для KB — модель M3; для проектов — модель M9
(гибрид, только для пересматриваемых).

**Аналогия из 1С:** это как если бы в M3 зафиксировали «для документов
используем только статусы», а в M9 выяснилось, что для некоторых
документов нужны ещё и версии. Решение правильное, но его надо явно
зафиксировать как изменение.

1. **Контекст** — какую задачу решаем.
