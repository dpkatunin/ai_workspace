# Правила ведения базы знаний

Единый источник правил для `kb/` и `_meta/`. Если правило здесь противоречит карточке — прав файл, карточку чиним. Минимальная версия. Финализация — после чекпоинта 2026-10 (см. `_meta/checkpoints/2026-10.md`).

Обновлено 2026-11-02: добавлены §10–13 (режимы работы агента, источники факта, отрицательный результат, мультиконфигурация). §1 обобщён на `config_id`.

## 1. Идентификаторы и имена

- `id` карточки: `<config_id>-<prefix>-<slug>`, где `config_id` — идентификатор конфигурации (`unf30` для УНФ 3.0), `prefix` ∈ {`doc`, `cat`, `reg`, `mech`, `pb`, `pit`, `case`}.
- Существующие id УНФ не меняются: `config_id = unf30`.
- `type` — отдельное поле frontmatter, **не** то же самое, что `prefix`. Один `type: object` может иметь `prefix` = `doc`, `cat` или `reg`.
- Имя файла: `<prefix>-<slug>.md`, **без** префикса `config_id`. `config` и `unf30-` живут только в `id`.
- `slug` — латиница, дефисы, без сокращений, отражает суть.
- ID неизменен после публикации. Переименование — только через новый ID + редирект в `by-synonym.md`.

## 2. Типы карточек

| Тип | Назначение | Пример |
|---|---|---|
| `object` | Документ, справочник, регистр | `unf30-doc-realizaciya` |
| `mechanism` | Сквозной механизм | `unf30-mech-rezervirovanie` |
| `playbook` | Процедура «как сделать» | `unf30-pb-otgruzka-s-rezervom` |
| `pitfall` | Кластер грабель «почему не работает» | `unf30-pit-rezervirovanie` |
| `case` | Паттерн из внедрения | `unf30-case-mebel-nestandart` |
| `decision` | ADR (архитектурное решение) | `adr-001` |
| `project` | Карточка проекта | — |

## 3. Статусы

- `draft` — черновик, не проверен на практике/ИТС.
- `verified` — проверен, эталон.
- `outdated` — устарел, не используется как основная карточка (агент обязан предпочесть актуальную).

**Политика draft → verified.** *Временная формулировка; финализируется в ADR-001 после чекпоинта 2026-10.*

- Срок жизни `draft` — не более одного спринта. Просроченный `draft` блокирует закрытие спринта.
- Проверяет: архитектор + пользователь (внедренец).
- Критерии перевода: (1) сверка с практикой или ИТС; (2) секция `## Движения` заполнена по регистрам; (3) все ссылки живые; (4) в `by-synonym` есть вход (если применимо).
- Ответ агента с `draft`-карточкой обязан явно помечать статус.

**Структурная чистота ≠ verified.** Карточка с идеальным frontmatter и заполненными индексами, но с непроверенным содержательным утверждением, остаётся `draft`. `verified` = все содержательные утверждения подтверждены практикой / ИТС / конфигурацией. Структура — необходимое, но недостаточное условие.

## 4. Frontmatter

Обязательные: `id`, `config`, `type`, `level`, `tags`, `status`, `updated`. Опциональные: `config_version`, `synonyms`, `related`, `source`, `project`.

Поле `registers` **отсутствует** в схеме. Движения парсятся из тела, секция `## Движения` (решение чекпоинта 2026-10; расширение схемы — предмет ADR-003).

Мета-файлы (`conventions.md`, `index.md`, `handover.md`, `checkpoints/*.md`) — рабочие документы, а не карточки. Фронтматтер у них отсутствует.

## 5. Ссылки

- Только на существующие `id` внутри `kb/` и `_meta/`.
- Внешние ссылки — в поле `source`, не в теле.
- Битая ссылка = блокер для `verified`.

## 6. `_meta/by-synonym.md`

- Синоним — разговорное слово или фраза пользователя.
- **R1 (приоритет при конфликте):** если термин ведёт и в `object`, и в `playbook`/`pitfall`/`mechanism` — синоним ведёт в `object`, а на остальное ставится кросс-ссылка в теле object-карточки.
- Каждый существующий синоним обязан вести в правильную карточку.
- Карточка без разговорного синонима — допустимо (типично для `playbook`).

## 7. `_meta/by-movement.md`

- Строка на каждый регистр, куда пишет хотя бы одна карточка базы.
- Колонка «Документы» — документы-писатели (только `object`).
- Колонка «Карточки» — все карточки KB, связанные с регистром (`object` / `mechanism` / `playbook` / `pitfall`), с приоритетом `object`.
- Если карточки нет — регистр остаётся в таблице, колонка «Карточки» = `—`.
- Источник истины для движений — секция `## Движения` в `object`-карточках.
- Для карточек типа `mechanism` секция `## Движения` не требуется — они не являются регистраторами.

## 8. Индексы

**По ADR-003 индексы генерируются скриптом `tools/build_indexes.py`. Ручное редактирование `by-synonym.md` и `by-movement.md` запрещено.**

- Источник истины — фронтматтер карточек (`synonyms`, `status`) и секция `## Движения`.
- Любая правка карточки, затрагивающая синонимы или движения, требует пересборки индексов в том же коммите:
  `py tools\build_indexes.py --apply`
- Пересобранные индексы (`_meta/by-synonym.md`, `_meta/by-movement.md`, `kb/unf30/_index.md`) коммитятся вместе с карточками.
- Расхождение индекса и карточки после пересборки — дефект скрипта, фиксируется в протоколе чекпоинта.
- Правка индекса руками без правки карточки — нарушение ADR-003, откатывается.

## 9. Изоляция источника

- `_source/` не читается агентом (ADR-002). Ссылки на `_source/` в карточках запрещены.

## 10. Режимы работы агента (теги)

Тег — первое слово сообщения пользователя. Регистр не важен. Тег действует на одно сообщение, не на весь чат. Неизвестный тег — уточнить, не угадывать. **Нет тега = `/kb`.**

| Тег | Назначение | Поведение |
|---|---|---|
| `/kb` (по умолчанию) | Ответ по базе знаний | `search_kb` первым действием; ответ только по карточкам с `id`; если топ нерелевантен — «нет в KB» и стоп |
| `/kb+` | Разведка, в KB может не быть | KB → CONFIG → GENERAL; GENERAL помечен «не верифицировано» |
| `/cfg` | Вопрос про метаданные | Только CONFIG (`search_config` / `read_config_file`); KB не используется |
| `/free` | Черновик, исследование | GENERAL разрешён; KB по желанию; ответ не для клиента |
| `/tags` | Шпаргалка | Выдать таблицу тегов и примеры из `design/10-cheatsheet.md` |

Правила режимов:
- `/kb` — безопасное поведение по умолчанию. Если пользователь не указал тег, агент работает как `/kb`.
- В `/kb` и `/cfg` имена объектов и реквизитов — только из CONFIG. GENERAL как источник имён запрещён.
- Переключение режима — только явным тегом. Агент не выбирает `/free` сам.
- Первый ответ в новом чате начинается строкой: «Режимы: /kb /kb+ /cfg /free /tags. По умолчанию /kb.»

## 11. Источники факта и маркировка

Три источника, три уровня доверия:

| Источник | Обозначение | Что даёт | Ограничение |
|---|---|---|---|
| База знаний | `KB` | Проверенные утверждения о поведении | Только то, что есть в карточках |
| Конфигурация (XML) | `CONFIG` | Точные имена объектов и реквизитов | Структура, не поведение |
| Общие знания модели | `GENERAL` | Гипотезы, формулировки поиска | **Не источник имён объектов** |

Правила:
- Имя объекта или реквизита может попасть в ответ только из `CONFIG`. Если `CONFIG` не подтвердил — писать «не подтверждено».
- Поведение («как работает», «что делать») — из `KB`. Если в `KB` нет — «нет в KB».
- `GENERAL` разрешён только в `/kb+` и `/free`; в `/kb+` каждый факт из `GENERAL` помечается «не верифицировано».
- Каждый факт в ответе маркируется: `KB (id)` / `CONFIG (файл)` / `не подтверждено` / `не верифицировано`.
- Приоритет при конфликте: для поведения — `KB`, для имён — `CONFIG`. Противоречие фиксируется, а не сглаживается.

## 12. Отрицательный результат поиска

- «Не найдено запросом X» **не равно** «объекта нет». Формулировка: «не подтверждено».
- Если `search_config` вернул «не найдено», агент обязан переформулировать запрос минимум дважды (синоним, часть имени, другой `kind`) до вывода «не подтверждено».
- Если `search_kb` вернул карточки с высокой релевантностью, но тематически не совпадающими с запросом, — это «нет релевантных карточек», а не «ответ найден». Признак: top-1 ниже порога или тема мимо.
- Запрещено после «не найдено» продолжать ответ деталями из `GENERAL` без пометки «не верифицировано».
- Playbook «в KB нет ответа» — в `design/00-START-HERE.md`.

## 13. Мультиконфигурация (черновик, ждёт ADR)

Правила, которые действуют уже сейчас:
- `config_id` — обязательная часть `id` карточки и пути `kb/<config_id>/...`.
- Карточки разных конфигураций не смешиваются в одной папке.
- `config` во frontmatter обязателен и совпадает с `config_id` в `id`.

Требует ADR (не решено):
- параметр `config` в MCP-инструментах `search_config`, `read_config_file`, `search_kb`;
- формат индексов при нескольких конфигурациях: общий с колонкой `config` или отдельные на конфигурацию;
- `config_id` в карточках проектов: реквизит, а не путь.

До принятия ADR новые конфигурации не заводятся; УНФ 3.0 остаётся единственной (`config_id = unf30`).
