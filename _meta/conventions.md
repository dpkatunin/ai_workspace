# Правила ведения базы знаний

Единый источник правил для `kb/` и `_meta/`. Если правило здесь противоречит карточке — прав файл, карточку чиним. Минимальная версия. Финализация — после чекпоинта 2026-10 (см. `_meta/checkpoints/2026-10.md`).

Обновлено 2026-11-02: §10-12 пересмотрены. Введено обязательное правило: **ответ в `/1c` без вызова `search_config` недействителен.** Добавлен §12.2 против зацикливания при подмене инструмента. Формат XML-выгрузки — `.xml`, не `.yaml`.

Обновлено 2026-11-03 (по итогам прогона 7 стресс-теста): §10 дополнен порядком для составных вопросов. §11 — введён источник `WEB` и требование вывода инструмента для каждого `CONFIG`-факта.

## 1. Идентификаторы и имена

- `id` карточки: `<config_id>-<prefix>-<slug>`, где `config_id` — идентификатор конфигурации (`unf30` для УНФ 3.0), `prefix` ∈ {`doc`, `cat`, `reg`, `mech`, `pb`, `pit`, `case`}.
- Существующие id УНФ не меняются: `config_id = unf30`.
- `type` — отдельное поле frontmatter, **не** то же самое, что `prefix`. Один `type: object` может иметь `prefix` = `doc`, `cat` или `reg`.
- Имя файла: `<prefix>-<slug>.md`, **без** префикса `config_id`. `config` и `unf30-` живут только в `id`.
- `slug` — латиница, дефисы, без сокращений, отражает суть.
- ID неизменен после публикации. Переименование — только через новый ID + редирект в `by-synonym.md`.

## 2. Типы карточек

| Тип | Назначение | Пример |
|---|---|---|
| `object` | Документ, справочник, регистр | `unf30-doc-realizaciya` |
| `mechanism` | Сквозной механизм | `unf30-mech-rezervirovanie` |
| `playbook` | Процедура «как сделать» | `unf30-pb-otgruzka-s-rezervom` |
| `pitfall` | Кластер грабель «почему не работает» | `unf30-pit-rezervirovanie` |
| `case` | Паттерн из внедрения | `unf30-case-mebel-nestandart` |
| `decision` | ADR (архитектурное решение) | `adr-001` |
| `project` | Карточка проекта | — |

## 3. Статусы

- `draft` — черновик, не проверен на практике/ИТС.
- `verified` — проверен, эталон.
- `outdated` — устарел, не используется как основная карточка (агент обязан предпочесть актуальную).

**Политика draft → verified.** *Временная формулировка; финализируется в ADR-001 после чекпоинта 2026-10.*

- Срок жизни `draft` — не более одного спринта. Просроченный `draft` блокирует закрытие спринта.
- Проверяет: архитектор + пользователь (внедренец).
- Критерии перевода: (1) сверка с практикой или ИТС; (2) секция `## Движения` заполнена по регистрам; (3) все ссылки живые; (4) в `by-synonym` есть вход (если применимо).
- Ответ агента с `draft`-карточкой обязан явно помечать статус.

**Структурная чистота ≠ verified.** Карточка с идеальным frontmatter и заполненными индексами, но с непроверенным содержательным утверждением, остаётся `draft`. `verified` = все содержательные утверждения подтверждены практикой / ИТС / конфигурацией. Структура — необходимое, но недостаточное условие.

## 4. Frontmatter

Обязательные: `id`, `config`, `type`, `level`, `tags`, `status`, `updated`. Опциональные: `config_version`, `synonyms`, `related`, `source`, `project`.

Поле `registers` **отсутствует** в схеме. Движения парсятся из тела, секция `## Движения` (решение чекпоинта 2026-10; расширение схемы — предмет ADR-003).

Мета-файлы (`conventions.md`, `index.md`, `handover.md`, `checkpoints/*.md`) — рабочие документы, а не карточки. Фронтматтер у них отсутствует.

## 5. Ссылки

- Только на существующие `id` внутри `kb/` и `_meta/`.
- Внешние ссылки — в поле `source`, не в теле.
- Битая ссылка = блокер для `verified`.

## 6. `_meta/by-synonym.md`

- Синоним — разговорное слово или фраза пользователя.
- **R1 (приоритет при конфликте):** если термин ведёт и в `object`, и в `playbook`/`pitfall`/`mechanism` — синоним ведёт в `object`, а на остальное ставится кросс-ссылка в теле object-карточки.
- Каждый существующий синоним обязан вести в правильную карточку.
- Карточка без разговорного синонима — допустимо (типично для `playbook`).

## 7. `_meta/by-movement.md`

- Строка на каждый регистр, куда пишет хотя бы одна карточка базы.
- Колонка «Документы» — документы-писатели (только `object`).
- Колонка «Карточки» — все карточки KB, связанные с регистром (`object` / `mechanism` / `playbook` / `pitfall`), с приоритетом `object`.
- Если карточки нет — регистр остаётся в таблице, колонка «Карточки» = `—`.
- Источник истины для движений — секция `## Движения` в `object`-карточках.
- Для карточек типа `mechanism` секция `## Движения` не требуется — они не являются регистраторами.

## 8. Индексы

**По ADR-003 индексы генерируются скриптом `tools/build_indexes.py`. Ручное редактирование `by-synonym.md` и `by-movement.md` запрещено.**

- Источник истины — фронтматтер карточек (`synonyms`, `status`) и секция `## Движения`.
- Любая правка карточки, затрагивающая синонимы или движения, требует пересборки индексов в том же коммите:
  `py tools\build_indexes.py --apply`
- Пересобранные индексы (`_meta/by-synonym.md`, `_meta/by-movement.md`, `kb/unf30/_index.md`) коммитятся вместе с карточками.
- Расхождение индекса и карточки после пересборки — дефект скрипта, фиксируется в протоколе чекпоинта.
- Правка индекса руками без правки карточки — нарушение ADR-003, откатывается.

## 9. Изоляция источника

- `_source/` не читается агентом (ADR-002). Ссылки на `_source/` в карточках запрещены.

## 10. Режимы работы агента

По умолчанию чат — обычный ассистент. Работа с 1С включается тегом.

| Команда | Назначение | Поведение |
|---|---|---|
| `/1c` | Режим 1С | До `/1c off`. Ответ строится по формуле: GENERAL (логика) + CONFIG (имена) + KB (поведение) |
| `/1c off` | Выключить | Обычный чат |
| `/tags` | Справка | Показать эту таблицу |
| `/project` | Зарезервирован | Для документации по проектам |

**Правило одного напоминания:** Если в обычном чате задан явно 1С-вопрос, агент один раз за сессию предлагает включить `/1c`.

**Порядок ответа в `/1c` (обязательный, по шагам):**

0. **Вызов `search_config` — до ответа.** Выбери из вопроса минимум одно имя объекта (документ, регистр, справочник) и вызови `search_config` по нему. Пока вызова не было — ответ не начинай.
1. **GENERAL — основа.** Дай полный, полезный ответ по логике работы, даже если в KB пусто. Не отказывай в ответе.
2. **CONFIG — проверка имён.** Каждое имя объекта, которое попадает в ответ, сверь с результатом `search_config` / `read_config_file`. Если имени нет в выдаче — пиши «требует проверки» или заменяй на подтверждённое.
3. **KB — проверка поведения.** Если в KB есть карточка с описанием поведения — используй её и ссылайся на `id`. Если нет — помечай общий ответ как «не верифицировано».
4. **Никаких отказов.** «В KB нет ответа» — это факт, а не повод молчать.

**Порядок для составных вопросов.**

Если вопрос требует нескольких сущностей или в KB нет покрытия, порядок расширяется:

1. `search_kb` — есть ли ответ в KB. Если top-1 ниже 0.85 или тема мимо — зафиксируй «нет в KB», укажи top-1 и переходи к шагу 2.
2. `WEB` — найди ответ во внешних источниках. Для каждого факта укажи, откуда взят (ИТС, вендорская статья, профильный сайт).
3. `search_config` — проверь **каждое** имя объекта из веб-ответа. Для каждого покажи вывод инструмента: найдено / не найдено / какой тип. Если имени нет в конфигурации — отбрось его или замени на подтверждённое и явно напиши, что отбросил.
4. Сборка — с маркировкой источников: `KB (id)` / `WEB (источник)` / `CONFIG` / «не верифицировано».

Ограничения шага:
- Не больше двух попыток на каждом шаге. Если `WEB` дважды не дал результата — переходи к `CONFIG` с тем, что есть.
- **Имя без вывода инструмента = «не подтверждено».** В финальный ответ как факт не идёт.
- Таблица `CONFIG` без вывода инструментов недействительна.

**Ответ без единого вызова `search_config` в `/1c` считается недействительным.** Если MCP недоступен — действует §12.1. Если харнесс подменяет инструмент — §12.2.

## 11. Источники факта и маркировка

| Источник | Обозначение | Роль |
|---|---|---|
| Общие знания | `GENERAL` | Логика, алгоритмы, бизнес-смысл. Основа ответа |
| Конфигурация (XML) | `CONFIG` | Имена объектов и реквизитов. Фильтр для GENERAL |
| База знаний | `KB` | Проверенное поведение. Дополнение к GENERAL |
| Внешние источники (ИТС, вендорские статьи, профильные сайты) | `WEB` | Пробел в KB. Даёт формулировку и контекст. Не даёт уровень метаданных — это делает CONFIG |

Правила:
- GENERAL даёт ответ. CONFIG проверяет имена. KB подтверждает поведение.
- Если в KB нет — ответ всё равно даётся, но с пометкой «не верифицировано».
- Если `search_config` не нашёл объект — переформулируй запрос минимум дважды. Если и это не помогло — пиши «требует проверки», но не отказывай в ответе.
- Факты в ответе маркируются: `KB (id)`, `WEB (источник)`, `CONFIG`, «не верифицировано».
- **Формат XML-выгрузки:** в `_raw/unf30_xml/` лежат файлы `.xml`, а не `.yaml`. Если `read_config_file` не находит файл — проверь расширение.
- **`WEB` не заменяет `CONFIG`.** Веб даёт правильное название («маркировка остатков»), CONFIG — где оно живёт (`ВидыОперацийИСМП.ВводВОборотМаркировкаОстатков`). Расхождение WEB ↔ CONFIG фиксируется в ответе явно.
- **Каждый `CONFIG`-факт — с выводом инструмента.** Таблица «✅» без вывода недействительна: имя без вывода = «не подтверждено».

**Якорный пример (почему это важно):**
Пользователь спрашивает про излишки при пересорте. По-русски логично сказать «документ "Ввод в оборот"». Но `search_config("ввод в оборот", kind="Document")` возвращает «не найдено» — такого документа нет. Есть `ВозвратВОборотИСМП` и `СписаниеКодовМаркировкиИСМП`. Без вызова CONFIG агент выдумает симметричное имя и соврёт.

## 12. Отрицательный результат поиска

- «Не найдено» ≠ «объекта нет».
- Если `search_config` не нашёл с первого раза — пробуй синонимы, часть имени, другой `kind`.
- Если `search_kb` вернул нерелевантные карточки — не используй их как ответ, но и не отказывай в ответе.
- После «не найдено» — дай ответ из GENERAL, проверь имена в CONFIG, пометь «не верифицировано».

## 12.1. Недоступность MCP (сбой инфраструктуры)

Это **не** «не найдено», а ошибка вызова инструмента: таймаут, отказ соединения, «сервер недоступен».

Правила:
1. **Одна повторная попытка.** Не три, не пять. Одна — на случай разового сбоя сети.
2. **Если снова ошибка — явно сообщи:** «MCP недоступен, проверка не выполнена: <имя инструмента>». Это факт для пользователя, а не оправдание.
3. **Дай ответ из GENERAL** с маркировкой «не верифицировано (MCP недоступен)».
4. **Предложи восстановить:** проверить, запущен ли `mcp_server.py`, вызвать `kb_stats` для проверки связи, перезапустить сервер.
5. **Не пиши «не проверял»** — это читается как лень. Пиши «MCP не отвечал» — это диагноз.

Разница:
- ❌ «имена объектов я не подтверждал» — неясно, почему.
- ✅ «MCP недоступен, имена не проверены» — понятно, что делать.

## 12.2. Подмена инструмента харнессом (зацикливание)

Отдельный сбой: `search_config` или `search_kb` вызывается, но харнесс возвращает не результат инструмента, а что-то другое — веб-поиск, заглушку, результат другого инструмента. Агент видит «не тот» ответ и повторяет попытку.

Правила:
1. **Две попытки — предел.** Если две попытки подряд вернули не тот инструмент или не тот результат — остановись.
2. **Сообщи явно:** «MCP-инструмент подменяется харнессом, проверка не выполнена: <что вернулось>».
3. **Дай ответ из GENERAL** с маркировкой «не верифицировано (MCP недоступен/подменён)».
4. **Не повторяй** больше двух раз. Зацикливание — дефект, а не настойчивость.
5. **Предложи диагностику:** вызвать `kb_stats`. Если он работает, проблема в конкретном инструменте, а не в MCP.

Пример:
- ❌ 19 попыток вызвать `search_config`, каждая возвращает «Найдено 29 веб-страниц». Потом лимит шагов.
- ✅ Две попытки → «MCP-инструмент подменяется веб-поиском» → ответ с пометкой.

## 13. Мультиконфигурация (черновик, ждёт ADR)

Правила, действующие сейчас:
- `config_id` — обязательная часть `id` карточки и пути `kb/<config_id>/...`.
- Карточки разных конфигураций не смешиваются в одной папке.
- `config` во frontmatter обязателен и совпадает с `config_id` в `id`.

Требует ADR:
- параметр `config` в MCP-инструментах;
- формат индексов при нескольких конфигурациях;
- `config_id` в карточках проектов.
