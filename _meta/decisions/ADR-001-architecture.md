# ADR-001: Архитектура базы знаний — принципы

## Контекст

База знаний по 1С:УНФ 3.0 должна обслуживать агента (DeepSeek + BDS) и выдерживать рост: сейчас 60 файлов исходника, в перспективе — несколько конфигураций и сотни карточек. Нужно зафиксировать базовые принципы до масштабирования, чтобы каждый раздел не делался «как удобно в моменте» и база не стала неоднородной через полгода.

Ограничения:
- Хранение — GitHub (private), без собственной инфраструктуры.
- Доступ агента — через fetch файлов, без векторной БД на старте.
- Ведение — один человек (внедренец), время на поддержку ограничено.
- Собеседник — эксперт 1С, не специалист по ИИ. Решения должны быть объяснимы через аналогии 1С.

## Решение

Приняты четыре принципа. Каждый — отдельное архитектурное решение, зафиксированное ниже.

### Принцип 1. Двухуровневый RAG: KB + Projects

База разделена на два уровня с разными правилами:
- **`kb/`** — общие знания по конфигурациям. Стабильны, версионируются по релизу конфигурации, не привязаны к клиенту.
- **`projects/`** — память конкретных проектов. Лёгкий механизм: паспорт + ADR. Без протоколов и ТЗ.

Аналогия из 1С: `kb/` — это типовой справочник, `projects/` — это документы конкретной организации. Смешивать нельзя: типовое знание переживает проекты, проектное знание умирает вместе с проектом.

**Альтернативы:**
- Одна свалка без разделения — отвергнуто: проектное решение начинает выдаваться за общую практику, агент теряет границу применимости.
- Тяжёлая память проектов (встречи, ТЗ, переписка) — отвергнуто: стоимость ведения превышает пользу, RAG тонет в шуме.

**Последствия:**
- Агент обязан различать уровни и не переносить проектное на общее без оговорки.
- Проектные карточки всегда имеют `level: projects` и `project: <id>`.

### Принцип 2. Навигационный RAG вместо векторного на старте

Поиск идёт по иерархии: `_meta/index.md` → `_index.md` раздела → 1–3 карточки. Векторные эмбеддинги не используются.

Аналогия из 1С: это иерархический справочник с группами. Сначала открываем группу (индекс), потом элемент (карточку). Не «поиск строки по всей базе», а осмысленный спуск по дереву.

**Почему не векторный RAG сейчас:**
- Требует инфраструктуры (модель эмбеддингов, векторное хранилище, переиндексация) — несовместимо с «GitHub + браузерный чат».
- На 60–100 карточках навигация точнее: агент физически читает карточку, а не «вспоминает» похожее.
- Даёт цитаты: агент ссылается на ID, а не на «где-то было».
- Дешевле в ведении: не надо переиндексировать при каждом изменении.

**Последствия:**
- Качество ответа зависит от качества индексов (`_index.md`, `by-synonym.md`, `by-movement.md`). Их надо вести.
- Агент обязан следовать навигатору, а не читать всё подряд.

**Условия пересмотра (триггеры перехода на векторный поиск):**
- Карточек больше ~150–200, и навигация начинает промахиваться на пилоте.
- Появляется вторая-третья конфигурация с пересекающимися терминами.
- Появляется инфраструктура (MCP-сервер с поиском), которая снимает стоимость владения.

До наступления триггеров векторный RAG не внедряется.

### Принцип 3. Разбиение playbook / pitfall

Процедуры («как сделать») и грабли («почему не работает») — разные типы карточек с разной структурой и разной скоростью изменения.

**Почему:**
- Разные вопросы → разные карточки. «Как отгрузить» и «почему не проводится» — разные запросы, агент не должен тащить оба.
- Разная структура: playbook — упорядоченные шаги; pitfall — отображение «симптом → причина → решение».
- Разная скорость изменения: playbook стабилен, pitfall растёт после каждого проекта. Вместе — правишь процедуру ради одной ошибки.

**Компромисс:** pitfall — кластер по теме, а не по разделу и не одна карточка на ошибку. 15–25 карточек на всю базу вместо 96 микрофайлов. Каждая ошибка — секция с якорем `{#pit-xxx}`.

**Последствия:**
- Больше файлов, чем при единой карточке «Практика».
- Playbook обязан ссылаться на релевантные pitfall в конце.
- Pitfall-кластеры пересекают разделы (резервы — из продаж, закупок, склада).

### Принцип 4. Статус достоверности — обязательное поле

Каждая карточка имеет `status: verified | draft | outdated`. Агент обязан указывать статус в ответе.

**Почему:**
- Без статуса агент не может отличить проверенное от черновика и выдаёт всё за достоверное.
- Это главный механизм управления галлюцинациями: не «модель умная», а «модель честно говорит, откуда взяла и насколько доверять».
- Аналогия из 1С: это как признак «Проверено» в справочнике — без него нельзя построить отчёт по качеству данных.

**Последствия:**
- `draft` нельзя цитировать как `verified`.
- `outdated` не используется как основное знание; в теле указывается, чем заменено.
- Ритуал: после проекта карточки, проверенные на практике, переводятся в `verified`.

## Общие последствия

- Каркас базы зафиксирован. Масштабирование идёт по этим принципам, а не «как удобно».
- Любое отклонение — новый ADR, а не тихое изменение.
- Стоимость владения: ведение индексов и статусов — регулярный ритуал, а не разовая работа. Без ритуала база гниёт (главный риск проекта).

## Условия пересмотра ADR-001

- Появление векторного поиска (см. триггеры принципа 2).
- Рост до второй конфигурации — пересмотр структуры `kb/` (сейчас `kb/unf30/`).
- Если ведение индексов окажется дороже пользы — пересмотр принципа 2 в сторону автоматической генерации индексов.
