# Архитектурные решения базы (ADR)

Здесь фиксируются решения о том, **как устроена сама база знаний**: уровни, типы карточек, способ поиска, обязательные поля, процессы ведения. Не путать с ADR проектов (`projects/<client>/decisions/`) — там решения по конкретному клиенту.

## Зачем

Решение, не зафиксированное письменно, — не решение. Через три месяца никто (включая автора) не вспомнит, почему выбрана навигация вместо векторного поиска и при каких условиях её надо пересматривать. ADR — это «регистр сведений» архитектурных договорённостей: хранит не только «что», но и «почему» и «когда пересмотреть».

## Правила

- Один ADR — одно решение. Не сваливать несколько в один.
- Обязательные секции: Контекст, Решение, Альтернативы, Последствия, Условия пересмотра.
- Статусы: `proposed`, `accepted`, `superseded`, `rejected`.
- Принятый ADR не удаляется и не переписывается. Если решение изменилось — создаётся новый ADR, старый помечается `superseded` со ссылкой на новый.
- Нумерация сквозная: `ADR-001`, `ADR-002`, …
