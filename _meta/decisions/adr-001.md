# ADR-001. Синонимы и политика `draft`

## Контекст

Baseline чекпоинта 2026-10 показал два независимых дефекта:

1. `by-synonym.md` поддерживался вручную и уже разошёлся с карточками. Q13 (заказ покупателя / заказ на производство) — оба объекта без синонимов, top-1 miss.
2. Политика `draft` не была зафиксирована письменно. Агент на baseline в Q9 назвал статус, на Q1 — нет. Поведение было случайным, а не правилом.

Retest дал прецеденты, на которые можно опереться: Q9 и Q15 — агент открыл `draft`-карточки, пометил статус в источниках и дал отдельную оговорку по достоверности, не выдав `draft` за `verified`.

## Решение

### R1. Единственный источник синонимов — фронтматтер карточки

Синоним объявляется полем `synonyms` во фронтматтере карточки:

```yaml
synonyms: [контрагент, юрлицо, ИП]
```

Правило добавления: синоним вносится, только если он **встречается в теле карточки** или в названии реквизита. Синоним «из головы» (как бы это назвал пользователь) — запрещён. Причина: синоним без опоры в тексте карточки ведёт к ответу, который карточка не покрывает, — то есть к той же галлюцинации, только через индекс.

### R2. `by-synonym.md` — производный артефакт

Файл генерируется из фронтматтера (см. ADR-003). Ручное редактирование запрещено. До внедрения ADR-003 файл остаётся ручным, но каждая строка должна соответствовать полю `synonyms` карточки — при расхождении прав карточка, а не индекс.

### R3. Политика `draft`

- `draft`-карточка **участвует** в поиске и в ответе. Не исключается — иначе теряется единственный источник знания по теме.
- Агент **обязан** указать `status: draft` в цитате `[id: ..., status: draft]`.
- Если ответ опирается преимущественно на `draft`-материал, агент **обязан** дать явную оговорку по достоверности в теле ответа, а не только в списке источников.
- Агент **не вправе** повышать статус: `verified` берётся из фронтматтера, а не выводится из «связности» или «непротиворечивости» содержания.

### R4. Приоритет при коллизии синонима

Если один синоним ведёт в `object` и в `pitfall` — в `by-synonym` допускаются обе строки, первой идёт `object`. Обоснование: вопрос «что это» задаётся чаще, чем «почему не работает», а `pitfall` доступен из `object` по cross-link.

## Обоснование (evidence)

| Источник ↕▾ | Что подтверждает ↕▾ |
|---|---|
| −Q9 retest | Агент открыл 2 `draft`-карточки, пометил статус, дал оговорку. Политика R3 выполнима |
| Q15 retest | То же, плюс `by-movement` как первый шаг |
| Q13 baseline | Синонимов нет → top-1 miss. R1/R2 закрывают этот класс |
| Q10, Q12 baseline | `false_gap` — карточка есть, но агент сказал «нет карточки». Причина — навигация, не синонимы; R1 не поможет, помогает правило 8 навигатора |
⚙

## Последствия

**Плюс:**

- Один источник истины для синонимов — карточка.
- Поведение на `draft` становится предсказуемым и проверяемым в чекпоинте.
- Расхождение индекса и карточки ловится автоматически (ADR-003).

**Минус:**

- Существующие 31 карточка поля `synonyms` не имеют — нужна миграция.
- Оговорка по `draft` шумит на первой линии поддержки (зафиксировано в Q9 как риск). Лечится верификацией, а не ослаблением правила.

## Что НЕ решено

1. Миграция поля `synonyms` в 31 карточку — входит в ADR-003.
2. Формальный протокол перевода `draft → verified` (кто, по какому критерию, что считается «проверкой на практике») — отдельный ADR, кандидат ADR-004.
3. Язык синонимов: только русский или допускается англоязычная терминология (`RAG`, `SKU`)? Открыто.

# ADR-003. Автоматизация индексов `by-synonym` и `by-movement`

## Контекст

Два инцидента подряд с одной причиной:

1. **Q14 baseline/retest.** `_index.md` описывал `doc-sdelnyy-naryad` как «фиксация выработки». Карточка покрывает ещё и начисление зарплаты с проводкой Дт 20.40 Кт 70. Агент на baseline сделал вывод «процедуры начисления в базе нет» — ложный отказ из-за одной строки в ручном индексе.
2. **Q15 retest.** `by-movement.md` отработал идеально — за один запрос, дешевле всех остальных маршрутов. Но он ручной: при следующем изменении карточек разъедется так же, как `_index.md`.

Вывод: ручной индекс — это **вторая копия знания**. Любая вторая копия расходится с первой. Это не вопрос дисциплины, это структурный дефект.

## Решение

Индексы `_meta/by-synonym.md` и `_meta/by-movement.md` **генерируются скриптом** из карточек. Ручное редактирование запрещено.

### Контракт парсера

**1. Фронтматтер карточки** — источник для `by-synonym.md`:

```yaml
id: unf30-cat-kontragent        # обязателен, уникален
type: object                    # object | mechanism | playbook | pitfall | case
status: draft                   # verified | draft | outdated
synonyms: [контрагент, юрлицо]  # опционально, список строк

**2. Секция `## Движения`** — источник для `by-movement.md`.

Формат: список регистров, в которые пишет документ.

```
## Движения
- Цены номенклатуры
- Продажи
```

Правило: **нет секции `## Движения` → карточка не является регистратором.** Это касается справочников и механизмов.

**3. Справочники и измерения.** Карточки с `type: object` и без секции `## Движения` попадают в отдельную секцию `by-movement.md` — «Справочники (не регистраторы)» — с указанием, в каких регистрах они выступают измерением. Формат секции в карточке:

```
## Участие в регистрах
- Расчёты с покупателями (измерение: Контрагент)
```

### Режимы работы скрипта

| Режим ↕▾ | Что делает ↕▾ |
|---|---|
| −`build` | Перезаписывает `by-synonym.md` и `by-movement.md` из карточек |
| `check` | Ничего не пишет, возвращает код 1 при расхождениях. Для CI и для чекпоинта |
⚙

### Валидация в режиме `check`

- Дубли `id`.
- Синоним ведёт на несуществующий `id`.
- Карточка без фронтматтера.
- `status` вне множества `{verified, draft, outdated}`.
- Карточка с секцией `## Движения`, но регистр не встречается ни в одной другой карточке (возможная опечатка в имени регистра).
- `by-synonym.md` / `by-movement.md` на диске отличаются от сгенерированных.

### Маркировка выходных файлов

В шапке сгенерированных файлов:

```
<!-- GENERATED by tools/build_indexes.py. Не редактировать вручную. -->
```

## Критерии приёмки

1. `build` на текущем репозитории даёт файлы, содержательно совпадающие с ручными (расхождения разобраны построчно, не «просто перезаписали»).
2. `check` возвращает 0 на чистом репозитории.
3. `check` возвращает 1, если в карточку добавлен синоним, а индекс не пересобран.
4. Повторный запуск `build` идемпотентен (дифф пустой).

## Что нужно до реализации

Эталоны формата — по одному файлу каждого вида:

- `kb/unf30/objects/doc-realizaciya.md` — `verified`, с секцией `## Движения`, несколько регистров.
- `kb/unf30/pitfalls/pit-ceny.md` — `draft`, без `## Движения`.
- `kb/unf30/objects/cat-kontragent.md` — справочник, с секцией `## Участие в регистрах` (создан в спринте «Контрагенты», 2026-10-28).

Без эталонов парсер будет написан под догадку о формате и развалится на первом же реальном файле.

## Последствия

**Плюс:**

- Расхождение индекса и карточки становится невозможным по построению.
- `check` в чекпоинте заменяет ручную сверку.
- Добавление карточки = одна правка (сама карточка), а не три.

**Минус:**

- Нужна миграция: 31 карточка без `synonyms` и, возможно, с нестандартной секцией `## Движения`.
- Скрипт — ещё одна сущность, которую надо поддерживать. Приемлемо: он детерминирован и покрыт `check`.

## Что НЕ решено

1. Где живёт скрипт: `tools/` в этом же репозитории (предпочтительно) или отдельный репозиторий.
2. Язык: Python (совпадает с будущим парсером конфигурации 1С) — предварительно да.
3. Генерация `_index.md` раздела — не входит в этот ADR. Это следующий шаг после `by-synonym`/`by-movement`; `_index.md` пока остаётся ручным, но под `check`-валидацией ссылок.

## История изменений
