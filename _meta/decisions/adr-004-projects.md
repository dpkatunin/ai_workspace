# ADR-004. Контур `projects/`: структура, границы, индексация

**Статус:** accepted
**Дата:** 2026-11-01
**Связанные:** ADR-002 (изоляция `_source/`), ADR-003 (генерация индексов), `design/03-architecture.md` (два репозитория, MCP), `design/05-open-questions.md` §2, §3, §7
**Закрывает:** §2 (заметки vs данные), §3 (приватный репо — принципиальная часть), §7 (граница «моё / клиентское / общее»)

## Контекст

`kb/` — общее публичное знание. Клиентского контура нет вообще: `projects/` упомянут в `03-architecture.md` и `schema.md`, но каталога не существует.

Первая же реальная работа упирается в вопрос «куда писать приватное». Без ответа либо клиентское знание утечёт в публичный `kb/`, либо не запишется никуда и потеряется.

Схема карточек (`schema.md`) уже содержит всё необходимое: `level: kb | projects`, тип `project`, поле `project` во фронтматтере. `search_kb` уже принимает параметр `level`. Контракт MCP менять не придётся — это принципиально, см. проектное ограничение в `03-architecture.md`.

Оставались четыре двусмысленности: структура каталогов, соотношение `raw`/`processed` и `draft`/`verified`, судьба «личного» знания, момент подключения MCP.

## Решение

### 1. Структура каталогов

```

projects/
_index.md                     реестр проектов (собирается по паспортам)
_templates/                   шаблоны: паспорт, карточка проекта
_personal/                    личные методики (не клиент)
_project.md
cards/
<project-slug>/
_project.md                 паспорт проекта (type: project)
cards/                      карточки знаний проекта (плоско)
context/                    клиент, процессы, оргструктура — не карточки
checklists/                 чек-листы настройки и приёмки
inbox/                      сырые заметки, MCP не видит

```

`cards/` — **плоско**, как `kb/`: префикс в имени файла (`pit-...md`, `pb-...md`). Дерево `objects/mechanisms/playbooks` не дублируем: в проекте десятки карточек, а не сотни, глубина только мешает навигации.

### 2. Две оси статусов — не смешивать

| Ось | Значения | Где живёт |
|---|---|---|
| Стадия обработки материала | `raw` → `processed` | папки: `inbox/` = raw, разобранное = `context/` или `cards/` |
| Достоверность знания | `draft` → `verified` → `outdated` | поле `status` во фронтматтере карточки |

Аналогия из 1С: `raw/processed` — это «файл лежит в папке обмена» против «файл разобран обработкой». `draft/verified` — «документ не проверен» против «проведён и сверен с первичкой». Разные вещи, живут в разных местах.

**Следствие:** значение `raw` во фронтматтере карточки не появляется никогда. Карточка всегда `draft | verified | outdated`. Всё, что `raw`, лежит в `inbox/` и в индекс не попадает — иначе агент выдаст сырую заметку за факт (риск из §2).

### 3. Граница «моё / клиентское / общее»

| Тип знания | Где | Кто видит |
|---|---|---|
| Общее, публичное | `kb/` | все, публичный репо |
| Клиентское | `projects/<project-slug>/` | приватный репо |
| Личное (методики, не привязанные к клиенту, но непубличные) | `projects/_personal/` | приватный репо |

«Личное» — псевдопроект в том же приватном репозитории. Третий репозиторий не заводим: администрирования больше, чем пользы, а граница «личное/клиентское» и так обеспечивается отдельным каталогом.

### 4. Репозитории — два

- `ai_workspace` — публичный: `kb/`, `_meta/`, `tools/`.
- `ai_workspace_projects` — приватный: `projects/` (включая `_personal/`).

Подтверждаем решение из `03-architecture.md`. Третий репозиторий не создаётся.

### 5. Идентификаторы

- `project-slug` — латиница, нижний регистр, дефисы. **Псевдоним, не юрлицо** (`alfa`, `client-042`). Реальное название — только внутри `_project.md`.
- `project-slug` не должен совпадать с кодом конфигурации (`unf30`, `erp`, `zup`, `bp`, `ka`, `ut`) — иначе ID столкнутся.
- `id` карточки проекта: `<project-slug>-<prefix>-<slug>`, например `alfa-pit-rezervirovanie`.
- Имя файла карточки: `<prefix>-<slug>.md`, без слага проекта — как в `kb/`.
- Фронтматтер карточки проекта: `level: projects`, `project: <project-slug>`, `config: <конфигурация клиента>`, `type`, `status`, `tags`, `updated`.
- `id` паспорта: `<project-slug>` без префикса (по `conventions.md`, тип `project`).
- Для `_personal/`: каталог `_personal/`, слаг `personal`, ID вида `personal-pit-<slug>`.

### 6. Индексация — что попадает в поиск, а что нет

| Путь | Векторный индекс | Почему |
|---|---|---|
| `projects/<slug>/cards/*.md` | **да**, `level: projects` | знания проекта |
| `projects/<slug>/_project.md` | **нет** | паспорт — метаданные сделки, NDA-риск |
| `projects/<slug>/context/*.md` | **нет** | читается по явному пути, когда агент ведёт проект |
| `projects/<slug>/inbox/**` | **нет** | сырьё (`raw`), может быть ошибочным |
| `projects/<slug>/checklists/*.md` | **нет** | артефакт исполнения; при переиспользовании выпускается в `kb/` как playbook |

**Правило: паспорт проекта не индексируется.** Паспорт — это элемент справочника «Контрагенты»: ИНН, договор, контакты, сроки. Он не отвечает на вопрос «как работает механизм», а векторный поиск не различает «карточку клиента» и «карточку знания». Если паспорт попадёт в индекс, агент сможет процитировать юрлицо или номер договора в ответе на технический вопрос — прямой NDA-риск при переезде MCP в облако.

Индексы `_meta/by-synonym.md` и `_meta/by-movement.md` **не смешиваются** с проектными: они остаются только для `kb/`. Синонимы проектов собираются в `projects/<slug>/_index.md`. Причина: клиентское словечко в публичном индексе — это утечка через публичный репозиторий.

### 7. MCP и `projects/` — этапы

| Этап | Что | Статус |
|---|---|---|
| 0 | MCP читает только `kb/unf30`. Проекты наполняются файлами, поиск по ним не работает | **действует сейчас** |
| 1 | MCP читает оба корня локально; `level` уже есть в `search_kb`, корни — через переменные окружения | после наполнения первого проекта |
| 2 | Приватный репо читается через GitHub API с токеном | при переезде на VPS |

Переход 0 → 1 не требует правки контракта инструментов. Это и есть проверка совместимости с переездом.

### 8. Выпуск проектного знания в `kb/`

Если знание перестало быть клиент-специфичным — оно переносится в `kb/` обезличенной карточкой (`case` или `pitfall`), в проекте остаётся ссылка по `id`.

Правило «один факт — одно место» (`conventions.md`) действует и между уровнями: факт не живёт одновременно в `projects/` и `kb/`.

### 9. NDA-гигиена

- Клиентские данные обезличиваются: «Клиент А», «Иванов И.И.».
- Ключи, пароли, персональные данные не хранятся нигде.
- Реальное юрлицо и номера договоров — только в `_project.md`, который не индексируется и лежит в приватном репо.
- Коммит в приватный репо не содержит ссылок на публичный `kb/` в обратную сторону.

## Обоснование

1. **Плоские `cards/`** — навигация по префиксу дешевле дерева; дерево оправдано от сотен карточек, в проекте их десятки.
2. **Две оси статусов** — прямое следствие §2: если смешать `raw` и `draft`, агент не сможет отличить «сырьё» от «черновика знания» и будет выдавать сырьё за факт.
3. **`_personal/` вместо третьего репо** — минус одно администрирование, минус одна точка отказа синхронизации. Если начнёт мешать — выделяется отдельным ADR.
4. **Отключённый MCP на этапе 0** — сначала проверяем структуру на живых данных, потом открываем агенту. Обратный порядок означал бы отладку схемы через поиск, то есть вслепую.
5. **Запрет индексации паспорта** — единственный риск, который нельзя починить постфактум: попавшее в ответ юрлицо уже утекло.
6. **Раздельные индексы** — публичный `by-synonym.md` коммитится в публичный репо. Любая клиентская строка там = утечка в истории Git, которую не откатить удалением файла.

## Последствия

- Появляется определённое место для клиентского знания; публичный `kb/` остаётся чистым.
- `schema.md` применяется к обоим уровням без изменений; `level` и `project` уже в схеме.
- `search_kb` получает второй корень на этапе 1 — без изменения сигнатуры.
- Появляется регулярная процедура: разбор `inbox/` → карточка или `context/`.
- Нужен шаблон карточки проекта и шаблон паспорта в `projects/_templates/`.
- `projects/_index.md` собирается по паспортам; ручное редактирование — до появления скрипта (см. ниже).

## Что осталось нерешённым

1. **Скрипт сборки `projects/_index.md`** — пока вручную; автоматизация после 2–3 проектов, когда станет видна реальная структура паспорта.
2. **Автоматизация `inbox/`** — на старте ручной разбор. Скрипт — когда поток заметок станет регулярным.
3. **Момент перехода на этап 1** (подключение MCP к `projects/`) — критерий: первый проект с ≥ 10 карточками, чтобы было что искать.
4. **Механизм выпуска в `kb/`** — правило есть, процедуры (кто, когда, как проверяет обезличивание) нет.
5. **Судьба `checklists/`** — считать ли их знанием при повторном использовании или всегда выпускать в `kb/` как playbook. Предварительно: выпускать.
6. **Проверка коллизий `project-slug` с кодами конфигураций** — сейчас правилом, не валидатором.
