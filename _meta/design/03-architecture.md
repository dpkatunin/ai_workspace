# Техническая схема

## Уровни знаний

```

kb/                — общее знание по конфигурациям (публично)
_shared/         — общее для всех конфигураций
unf30/           — УНФ 3.0
erp/             — 1С:ERP (план)
projects/          — данные клиентов (приватно)
_meta/             — правила, карта, индексы, ADR, design
_source/           — архив исходников (агент не читает)
_raw/              — XML-выгрузки (локально, в Git не идёт)

```

Мультиконфигурация заложена: `kb/<config>/`, а не `kb/unf30/` жёстко.

## Три уровня инфраструктуры

| Уровень | Роль | Что хранит |
|---|---|---|
| **GitHub** | Источник истины | Вся история, коммиты, откат |
| **VPS** | Витрина с MCP | Рабочая копия + сервер поиска |
| **Ноутбук** | Редактор + бэкап | Рабочая копия + локальный `rsync` |

Правило: **правим на ноутбуке → пушим в GitHub → VPS подтягивает (`git pull`)**. Сервер не редактируем, иначе история разъедется.

## Два репозитория

- **`ai_workspace`** — публичный: `kb/`, `_meta/`, `tools/`. Методичка, не жалко.
- **`ai_workspace_projects`** — приватный: `projects/`. Клиентские данные, NDA.

Причина: публичный репо читается с телефона при выключенном ноуте (raw-ссылки). Приватный — только через MCP с токеном. Разделение снимает риск утечки.

## MCP-сервер

### Текущее состояние

Локально на ноутбуке, `127.0.0.1:8000`, читает `kb/unf30/`, поиск векторный (fastembed).

Инструменты: `search_kb`, `get_card`, `kb_stats` — только чтение. Запись — отдельная разработка (`create_note` через GitHub API), не сейчас.

### Переезд в облако — отложен, но проектируется

**Решение:** переезд MCP на VPS **отложен** (не «когда-то потом забудем», а «отложено с проектной совместимостью»). Причины:
- Сейчас критичности нет — работаем с ноутбука.
- Нужно время, чтобы понять реальную нагрузку и требования.
- Переезд — это администрирование (обновления, ротация токенов, мониторинг), к которому нужна готовность.

**Проектное ограничение (действует постоянно):** любое архитектурное решение должно допускать миграцию MCP в облако **без переделки**. Это значит:

| Решение | Требование к совместимости с облаком |
|---|---|
| Структура `kb/` | Пути не зависят от ОС и локальных путей |
| Формат карточек | Самодостаточный, переносимый (markdown + YAML frontmatter) |
| MCP-инструменты | Работают одинаково локально и удалённо; никаких `file://` путей в контракте |
| Аутентификация | Закладывается сразу (Bearer-токен), даже если локально не нужна — чтобы переезд не потребовал переписывать протокол |
| Синхронизация | Опирается на `git pull`, а не на «скопировать файл» |
| Приватный репо | Чтение через GitHub API с токеном — работает и локально, и в облаке |
| Зависимости | requirements фиксированы, версии Python совместимы |
| Конфигурация | Через переменные окружения, не хардкод путей |

**Критерий готовности к переезду:** если завтра переехать — потребуется только перенос файлов, настройка HTTPS и токена. Никаких правок кода MCP, структуры или форматов.

**Триггеры для переезда** (когда «станет критично»):
- Регулярная работа с телефона при выключенном ноуте.
- Второй пользователь (коллега, РП).
- Клиентские встречи, где нужен доступ «здесь и сейчас».
- Рост базы, при котором локальный поиск тормозит.

### Будущее состояние (для планирования)

Переезд на VPS. Требования:
- HTTPS (Caddy + Let's Encrypt).
- Bearer-токен (обязателен, не «потом»).
- Файрвол (22/80/443).
- systemd для автозапуска.
- `git pull` по cron или вручную.
- Приватный репо через GitHub API с токеном.

## Масштабирование

| Карточек | Что нужно |
|---|---|
| до 100 | Текущая схема |
| 100–500 | `search-index.json` (превью вместо чтения `_index.md` целиком), чанкинг карточек, гибридный поиск (вектор + BM25) |
| 500–2000 | Мультиконфиг-поиск (`config` как параметр), дедупликация |
| 2000+ | Векторная БД (pgvector), реранкер |

Порог боли — ~150–200 карточек. Проектировать надо сейчас, переделывать потом больно.

## Пайплайн сырья

```

_source/ (PDF, статьи, курсы)
→ pdf_extract.py (извлечение, отсев шума)
→ chunker.py (смысловые чанки)
→ фильтр на входе: (1) функциональность или маркетинг? (2) дубль? (3) проверяемо?
→ агент: черновик карточки (draft)
→ verify_content.py: L2-сверка с XML-конфигурацией
→ человек: закрыть ⚠️ (L3)
→ build_indexes.py --apply
→ коммит

```

Узкое место — шаг «человек: закрыть ⚠️». Цель — свести его к 5–10 минутам на карточку.

## Что отложено

- **MCP в облако** — см. выше: отложен, но проектируется с учётом.
- **XML-парсер `RegisterRecords`** — сейчас `Registers with writers: 0`. Не влияет на валидацию имён, но без него не работает автопроверка «кто в кого пишет». Чинить — когда дойдёт до массовой верификации.
- **Запись через MCP** — заметки с телефона сейчас через копирование в чат.
- **Проектные карточки в поиске MCP** — после настройки чтения `projects/`.
