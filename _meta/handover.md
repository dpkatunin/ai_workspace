# Паспорт проекта: База знаний 1С для RAG-агента

Этот файл — точка входа для нового чата или нового участника. Он описывает текущее состояние проекта, архитектуру и следующие шаги.

## 1. Что мы строим
Мы создаем базу знаний по 1С:УНФ 3.0 для RAG-агента (внедренца-аналитика). Репозиторий: `github.com/dpkatunin/ai_workspace`.
Главная цель: агент должен отвечать на вопросы по внедрению, опираясь на проверенные карточки, с обязательной цитатой (`id`) и статусом достоверности (`verified` / `draft`).

## 2. Архитектура (зафиксирована в ADR-001 и ADR-002)
- **Двухуровневый RAG:** `kb/` (общие знания) + `projects/` (память проектов).
- **Изоляция источника:** старые исходники лежат в `_source/` и **не читаются** агентом.
- **Типы карточек:** `object`, `mechanism`, `playbook`, `pitfall`, `case`.
- **Навигация:** иерархическая (`_meta/index.md` → `_index.md` → 1–3 карточки). Векторный поиск пока не используем.

## 3. ⚠️ ПРАВИЛО ДЛЯ НОВОГО ЧАТА: НЕ ДЕЛАТЬ FETCH ВСЕГО РЕПОЗИТОРИЯ

**Критично для экономии контекста.** Каталог `_source/` содержит ~60 файлов исходников, которые НЕ участвуют в RAG. Если сделать fetch всего репозитория, `_source/` приедет в контекст и съест 80–100K токенов зря.

**Что делать вместо этого:**
- Запросить fetch **только** `_meta/` и `kb/unf30/` (по отдельности).
- Или попросить пользователя приложить вручную: `_meta/handover.md`, `_meta/index.md`, `kb/unf30/_index.md`, `_meta/by-synonym.md`, `_meta/by-movement.md`.
- `_source/` не открывать **никогда** — это архив по ADR-002.

Это правило действует и для ревью после спринта: проверять только `kb/unf30/`, `_meta/by-*`, `_meta/handover.md`, `_meta/index.md`. Не тянуть `_source/`.

## 5. Цель Фазы 2 (зафиксирована)
**Полный торговый контур** — до ~33 карточек. Не полный охват УНФ (это Фаза 3, требует пересмотра ADR-001 и, возможно, парсера конфигурации).

Осталось до цели Фазы 2 (2 спринта):
1. **Деньги:** касса/банк, эквайринг, подотчёт + грабли. ← **следующий спринт**
2. **Контрагенты/договоры:** базовая карточка + грабли.

Продажи углублённо (счёт на оплату, поступление на счёт) — по результатам чекпоинта, только если реальные вопросы агента покажут пробел.

## 6. Чекпоинт на 30 карточках
Когда в `kb/unf30/` наберётся ~30 карточек, сделать **чекпоинт архитектуры**. Сейчас 28 — до чекпоинта **один спринт** (деньги). После него планируем чекпоинт **перед** спринтом «Контрагенты», а не после:
- Прогнать 10–15 реальных вопросов через агента.
- Зафиксировать, где навигация промахивается, где карточек не хватает, где формат неудобен.
- По результатам — либо скорректировать ADR-001 (новый ADR), либо подтвердить текущую архитектуру.
- Отдельно проверить: не пора ли автоматизировать генерацию `by-synonym` и `by-movement` (ручное ведение на 30+ карточках начинает занимать заметное время).

**Этот чекпоинт не пропускать.** Он снимает риск «делаем вслепую и потом переделываем».

## 7. Как мы работаем (Workflow)
1. Я (Архитектор) генерирую ZIP-архив с новыми/измененными файлами.
2. Пользователь распаковывает в `C:\ai_workSpaceGitHub\ai_workspace` (с заменой).
3. Commit + Push через GitHub Desktop.
4. Проверка результата — **только fetch нужных каталогов**, не всего репозитория (см. п.3).
5. Спринты по 3 карточки. Кейсы — по 2 за спринт (они длиннее).

**Замечание по ZIP:** в одном из ранних спринтов 4 файла `_meta/*` при распаковке обрезались до заголовков. После каждой распаковки проверять глазами `handover.md` и `index.md` — они самые критичные.

## 8. Замечание про переезд
Если контекст чата переполняется — не тянуть до последнего. Симптомы: агент начинает ссылаться на состояние из своих предыдущих сообщений, а не из файлов. В этот момент: обновить этот handover → открыть новый чат → приложить `handover.md`, `index.md`, `kb/unf30/_index.md` (без `_source/`).
