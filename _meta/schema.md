# Схема карточек

Все карточки — Markdown с YAML front matter. Фронтматтер — это «реквизиты элемента справочника»: по ним агент фильтрует и связывает, не читая тело.

## Обязательные поля

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Уникальный ID. Формат: `<config>-<type>-<slug>`, например `unf30-doc-realizaciya`. |
| `config` | string | Конфигурация: `unf30`, `erp`, `zup`, ... |
| `type` | enum | `object`, `mechanism`, `playbook`, `pitfall`, `case`, `decision`, `project`. |
| `level` | enum | `kb` — общие знания, `projects` — конкретный проект. |
| `tags` | list | Свободные теги для отбора. |
| `status` | enum | `verified`, `draft`, `outdated`. |
| `updated` | date | Дата последнего изменения, `YYYY-MM-DD`. |

## Опциональные поля

| Поле | Тип | Описание |
|---|---|---|
| `config_version` | string | Минимальная версия конфигурации, например `">=3.0.12"`. |
| `synonyms` | list | Разговорные синонимы для поиска. |
| `related` | list | ID связанных карточек (граф). |
| `source` | string | Источник знания: ИТС, статья, проект. |
| `project` | string | ID проекта (только для `level: projects`). |

## Типы карточек

### `object` — объект метаданных или справочник
Документ, справочник, регистр. Отвечает на вопрос «что это и из чего состоит».
Секции: назначение, реквизиты, движения, связи, типовые ошибки (ссылки), источники.

### `mechanism` — механизм
Сквозная логика, которая не привязана к одному объекту: резервирование, скидки, ордерная схема, партионный учёт.
Секции: суть, где включается, как работает, подводные камни, связи.

### `playbook` — процедура
Пошаговое «как сделать». Отвечает на вопрос «как выполнить задачу».
Секции: когда применять, шаги, проверка результата, связанные грабли.

### `pitfall` — кластер грабель
Отображение «симптом → причина → решение». Кластер по теме, а не по разделу.
Каждая ошибка — отдельная секция с якорем `{#pit-xxx}`.
Секции: симптом, причина, решение, связанные карточки.

### `case` — паттерн из внедрения
Обезличенный опыт: контекст, решение, цифры, применимость.
Без маркетинга. Секции: контекст, решение, нестандартные приёмы, результаты, когда применять.

### `project` — паспорт проекта
Только для `level: projects`. Минимум полей, ссылки на ADR.

### `decision` — ADR
Запись архитектурного решения проекта.
Секции: контекст, решение, альтернативы, последствия.

## Пример фронтматтера

```yaml
---
id: unf30-doc-realizaciya
config: unf30
config_version: ">=3.0.12"
type: object
level: kb
tags: [продажи, отгрузка, резерв, ндс]
synonyms: [реализация, расходная накладная, отгрузка]
status: verified
source: "ИТС, разд. Продажи"
updated: 2026-10-26
related: [unf30-pb-otgruzka-s-rezervom, unf30-pit-rezervirovanie]
---
```

# Правила ведения базы

## ID карточек

Формат: `<config>-<prefix>-<slug>`.

- `config`: `unf30`, `erp`, `zup`, `bp`.
- `prefix`: `doc`, `cat`, `reg`, `mech`, `pb`, `pit`, `case`, `adr`.
- `slug`: латиница, дефисы, без пробелов. Смысловой, не порядковый.

Примеры: `unf30-doc-realizaciya`, `unf30-mech-rezervirovanie`, `unf30-pb-otgruzka-s-rezervom`, `unf30-pit-rezervirovanie`.

## Соответствие `type` и префикса ID

Поле `type` во фронтматтере — это тип карточки (что она описывает). Префикс в `id` — это тип объекта. Для объектов метаданных они расходятся:

| `type` | Префикс `id` | Когда |
|---|---|---|
| `object` | `doc` | документ |
| `object` | `cat` | справочник |
| `object` | `reg` | регистр |
| `mechanism` | `mech` | сквозной механизм |
| `playbook` | `pb` | процедура |
| `pitfall` | `pit` | кластер грабель |
| `case` | `case` | паттерн из внедрения |
| `decision` | `adr` | архитектурное решение |
| `project` | — | `id` = имя клиента, без префикса |

Это не ошибка, а разное назначение полей. Префикс помогает в навигации по ID, `type` — в машинной фильтрации.

## Имена файлов

`<prefix>-<slug>.md` в соответствующей папке:
- `objects/doc-realizaciya.md`, `objects/cat-nomenklatura.md`, `objects/reg-zapasy.md`
- `mechanisms/mech-rezervirovanie.md`
- `playbooks/pb-otgruzka-s-rezervom.md`
- `pitfalls/pit-rezervirovanie.md`
- `cases/case-mebel-nestandart.md`

Никаких пробелов, склейки слов и кириллицы в имени файла.

## Статусы

| Статус | Когда ставить |
|---|---|
| `verified` | Проверено на практике или по актуальному ИТС. Можно цитировать как достоверное. |
| `draft` | Черновик, не проверено. Агент обязан это указать в ответе. |
| `outdated` | Устарело (старая версия, изменился механизм). Агент не должен использовать как основное. |

## Ссылки

Связи только по `id` в поле `related`. В тексте — ссылки на ID, а не на имена файлов. Это защищает от переименований.

## Один факт — одно место

Если факт встречается в двух карточках — это ошибка. Оставляем в одной (обычно в `object` или `mechanism`), во второй — ссылка.

## Разделение playbook и pitfall

- **playbook** — процедура «как сделать». Стабильна, меняется редко.
- **pitfall** — грабли «почему не работает». Кластер по теме. Растёт после каждого проекта.

Не смешивать. Playbook ссылается на релевантные pitfall в конце.

## Служебные каталоги и служебные символы

- Каталоги с ведущим `_` (`_meta/`, `_source/`) — служебные. `kb/` и `projects/` — рабочие.
- Служебные теги разметки (например, `</BDS:create_file>`, HTML-комментарии-маркеры) в тело карточек не попадают. Если такой попал — удалить при следующей правке карточки.

## Каталог `_source/`

`_source/` — исходные материалы (старые файлы, выгрузки, черновики), из которых перерабатываются карточки. **Не используется для ответов.** См. ADR-002.

## Как добавить карточку

1. Выбрать тип и папку.
2. Взять шаблон из `templates/`.
3. Заполнить фронтматтер (все обязательные поля).
4. Записать тело по секциям типа.
5. Добавить ID в `_index.md` раздела и, если нужно, в `_meta/by-synonym.md`.
6. Проверить, что нет дублей фактов и нет ссылок на несуществующие ID.

## Обновление

При изменении карточки — обновить `updated`. При устаревании — поставить `status: outdated` и указать в теле, чем заменено.

## Приватность

- Клиентские данные — обезличенно: «Клиент А», «Иванов И.И.».
- Ключи, пароли, персональные данные — не хранить.
- Репозиторий — private.
