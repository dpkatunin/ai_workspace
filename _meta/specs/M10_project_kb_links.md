# M10. Связь проекта с KB

**Статус:** ✅ fixed
**Дата фиксации:** 2026-10-25
**Связанные:** M1 (адресация), M2 (связи), M3 (версии), M7-full (маршрутизация), M8 (валидация, отложен), M9 (структура проекта), M12 (changelog), M13 (генерация), M16 (кросс-проектный)
**Исправлено:** 2026-10-25 (добавлен `scenarios` в раздел 3.7)

---

## 1. Контекст

**Какую задачу решаем.** Проектные артефакты (mapping.md, gap.md,
to-be.md) генерируются на основе KB-файлов. Нужно:

1. **Зафиксировать**, какие KB-файлы использованы в проекте.
2. **Отслеживать**, что KB-файл обновился (M12) — и предупредить проект.
3. **Не ломать** ссылки при переименовании (M1) или удалении KB-файла.
4. **Обогащать KB** обратной связью из проектов (кейсы, грабли).

**Ключевые требования (из UX):**
- Пользователь не думает о ссылках — система сама отслеживает.
- Не «требовать ревью» при каждом исправлении запятой в KB.
- Архивные проекты не трогать.
- Массовое обновление KB — не 50 флагов, а один список.

**Аналогия из 1С.** Это как **связь документа со справочником**.
Документ «Реализация» ссылается на «Контрагента». Если контрагент
переименован — документ видит новое имя. Если помечен на удаление —
документ не ломается, но показывает предупреждение.

## 3. Решение

### 3.1. Где хранятся ссылки

**Два места:**

**1. `meta.yaml` — ключевые ссылки (10–15):**

```yaml
# meta.yaml
kb_links:
  - unf/sales/reference
  - unf/warehouse/practical
  - unf/pricing/reference
```

**Что считать «ключевыми»:**

- Файлы, которые определяют проект (например, `unf/sales/reference`,
если проект про продажи).
- Файлы, на которые ссылаются несколько артефактов.
- Не более 10–15 ссылок. Иначе `meta.yaml` раздуется.

**Кто определяет:** M13 при генерации предлагает (по частоте
использования в артефактах), человек подтверждает.

**2. `frontmatter` артефактов — ссылки конкретного артефакта:**

```
---
title: "Карта соответствия"
related_kb:
  - unf/sales/reference
  - unf/warehouse/practical
---
```

**В тексте — для читателя:**

```
### Продажи
Процесс «Заказ → Отгрузка» покрывается штатно
(см. `unf/sales/reference`).
```

**Почему оба:** frontmatter — для машины (M8, M13, M7-full), текст —
для человека.

### 3.2. Обратный индекс `_indexes/kb-usage.yaml`

**Что в индексе:**

```
# _indexes/kb-usage.yaml
unf/sales/reference:
  used_by:
    - project: aquaservice
      artifacts: [mapping.md, gap.md]
    - project: romashka
      artifacts: [to-be.md]
unf/warehouse/practical:
  used_by:
    - project: aquaservice
      artifacts: [mapping.md]
```

**Кто обновляет:** фоновое задание `tools/build_kb_usage.py` при коммите
(как `build_indexes.py` из M2).

**Что делает:**

1. Проходит по всем `meta.yaml` и `frontmatter` артефактов.
2. Пересчитывает `_indexes/kb-usage.yaml`.
3. Если что-то изменилось — добавляет в коммит.

**Ручной запуск:** если нужно срочно (например, при миграции KB).

### 3.3. ⚠️ Важное уточнение: `requires-review` только при `change_type: breaking`

M3 ввёл `change_type` при обновлении KB-файла. M10 использует его
для решения, ставить ли `requires-review` проекту.

| `change_type` | Что означает | `requires-review` проекту? |
|---|---|---|
| `initial` | Первая версия | ❌ **Нет** (проект не мог ссылаться раньше) |
| `additive` | Дополнение (старое актуально) | ⚠️ **Опционально** (человек решает) |
| `breaking` | Замена (смысл изменился) | ✅ **Да** (проект может содержать устаревший вывод) |
| `fix` | Исправление (опечатка) | ❌ **Нет** (смысл не изменился) |

**Почему это критично:** если KB-файл обновился с `fix`, проект не
должен получать `requires-review`. Иначе при каждом исправлении запятой
все проекты будут «требовать ревью» — это шум, который обесценивает флаг.

**Аналогия из 1С:** это как **«Вид операции» документа**. Не каждый
документ создаёт движения — только определённые виды операций. Не каждый
`change_type` ставит `requires-review` — только `breaking`.

### 3.4. Что происходит при обновлении KB

**Алгоритм:**

1. KB-файл обновился (M3) с `change_type: breaking`.
2. M12 ставит `requires-review` на KB-файл.
3. M10 проходит по `_indexes/kb-usage.yaml` и находит все проекты,
которые на него ссылаются.
4. Каждому такому проекту (если не `archived`) добавляется запись
в `kb_updates_pending`:

```
# meta.yaml
kb_updates_pending:
  - kb_file: unf/sales/reference
    change_type: breaking
    updated_at: 2026-10-25
  - kb_file: unf/warehouse/practical
    change_type: additive
    updated_at: 2026-10-25
```

5. Пользователь видит при открытии проекта: «3 KB-файла обновились
(2 — breaking, 1 — additive). Проверьте артефакты: mapping.md, gap.md».

**Почему агрегировать:** 50 отдельных флагов — это шум. Один список
с группировкой по `change_type` — это обзор.

**Аналогия из 1С:** это как **«Групповая обработка»** — выбрал 50
документов, провёл одной командой. Не 50 отдельных операций.

### 3.5. Что происходит при удалении KB

**KB-файл не удаляется, а помечается `deprecated`** (M3, `status: deprecated`).

**Проект, ссылающийся на `deprecated`-файл:**

- Получает `requires-review`.
- При открытии — предупреждение: «KB-файл `unf/sales-old/reference`
помечен как устаревший. Рекомендуется заменить на `unf/sales/reference`».

**Почему не удалять:** удаление ломает ссылки. `deprecated` — это как
«Пометка на удаление» в 1С: объект остаётся, но не используется.

### 3.6. Архивные проекты

**Архивные проекты не трогаем при обновлении KB.**

**Почему:**

- Проект закрыт, его никто не смотрит.
- Если клиент вернётся — при переводе в `active` M10 проверит все
ссылки и покажет `requires-review`.
- Не засоряем `meta.yaml` флагами для закрытых проектов.

**Исключение:** если KB-файл помечен `deprecated`, а проект на него
ссылается — даже архивный проект получает предупреждение (при
следующем открытии). Это не «требует ревью», а «битая ссылка».

**Аналогия из 1С:** это как **«Помеченные на удаление»** — не участвуют
в работе, но остаются в базе. Когда «распометишь» — проверишь актуальность.

### 3.7. Какие артефакты ссылаются на KB

| Артефакт ↕▾ | Ссылается? ↕▾ | Почему ↕▾ |
|---|---|---|
| −`mapping.md` | ✅ Да | Каждый пункт → KB |
| `gap.md` | ✅ Да | Каждый разрыв → KB |
| `to-be.md` | ✅ Да | Модель → KB |
| `requirements.md` | ✅ Да | Требования → KB |
| `roadmap.md` | ✅ Да | Этапы → KB |
| **`scenarios.md`** | ✅ **Да** | **Сценарии → KB (как это делается в 1С)** |
| `checklist.md` | ⚠️ Опционально | Общие вопросы |
| `notes.md` | ❌ Нет | Сырьё |
| `meetings/*.md` | ❌ Нет | Факты |
| `system-passport.md` | ⚠️ Опционально | Если настройки описаны в KB |
⚙

**Правило:** если артефакт генерируется M13 на основе KB — он должен
ссылаться на KB. Если это сырьё или факт — не должен.

**M8 (линт) проверяет:** у генерируемых артефактов есть `related_kb`
в frontmatter. Если нет — предупреждение.

### 3.8. Обратная связь (KB ← проект)

**Три канала:**

| Канал ↕▾ | Что ↕▾ | Куда в KB ↕▾ |
|---|---|---|
| −**Кейсы** | «Как решали в проекте X» | `type: case` в `_configs/{config}/cases/` |
| **Грабли** | «Ошибка Y, решение Z» | `type: practical` в `_configs/{config}/{section}/practical.md` |
| **Новые знания** | Если проект выявил что-то, чего нет в KB | `type: reference` в `_configs/{config}/{section}/reference.md` |
⚙

**Кто решает:** полуавтомат.

- M13 предлагает: «Этот инцидент — новый кейс. Добавить в KB?»
- Внедренец решает: да / нет / отложить.

**Почему не автоматически:** не каждый инцидент — это знание. Некоторые —
частный случай.

**Почему не только вручную:** внедренец забудет. M13 напоминает.

**Запись — `updates_kb` в `meta.yaml`:**

```
updates_kb:
  - type: case
    title: "Импорт с ГТД: как обошли таможню как контрагента"
    status: proposed  # proposed | accepted | rejected
    proposed_by: M13
    proposed_at: 2026-10-25
  - type: practical
    title: "Ошибка «не хватает запасов»: склад в заказе"
    status: accepted
    accepted_at: 2026-10-25
```

**Только активные/принятые.** Отклонённые — не хранить (git log покажет).

**Почему в `meta.yaml`:** это проектное решение (что мы взяли в KB
из этого проекта). Логично рядом с `kb_links` (что мы взяли из KB
в проект).

**Аналогия из 1С:** это как **«Регистрация изменений»** — что из
проекта пошло в типовую, а что осталось клиентским.

### 3.9. Битые ссылки

**M8 (линт) — отложен** (средний приоритет). Пока M8 нет — M7-full
при запросе «покажи проект X» проверяет ссылки.

**Что показывать:**

> «Проект ссылается на `unf/sales-old/reference`, которого нет в KB.
> Возможные причины: файл переименован, удалён, или ссылка ошибочна».

**Что должен делать M8 (когда появится):**

1. Проверять все `related_kb` в frontmatter артефактов.
2. Проверять все `kb_links` в `meta.yaml`.
3. Проверять обратный индекс `_indexes/kb-usage.yaml`.
4. Показывать список битых ссылок.

### 3.10. Границы

| Механизм ↕▾ | Что делает ↕▾ | Граница с M10 ↕▾ |
|---|---|---|
| −**M2** | Связи внутри KB (KB-файл → KB-файл) | M10 — между уровнями (проект → KB) |
| **M7-full** | Поиск (маршрутизация запроса) | M10 готовит данные, M7-full использует |
| **M13** | Генерация артефактов | M13 использует `kb_links` и `related_kb` |
| **M8** | Валидация (линт) | M8 проверяет ссылки (отложен) |
⚙

**Аналогия из 1С:**

- M2 — «Связи справочников» (Номенклатура → Категория).
- M10 — «Связи документа со справочником» (Реализация → Номенклатура).
- M7-full — «Поиск документа» (отбор, сортировка).
- M13 — «Загрузка данных» (создание элементов).
- M8 — «Проверка ведения учёта» (валидация).

## 4. Почему так (обоснование)

### Почему два места для ссылок

**Только `meta.yaml`:** не видно, какой артефакт на что ссылается.
Все ссылки в одном месте — непонятно, откуда взялся вывод.

**Только `frontmatter`:** не видно «ключевых» ссылок проекта. Чтобы
понять, о чём проект, надо открыть все артефакты.

**Два места:** `meta.yaml` — обзор, `frontmatter` — детали. Как в 1С:
реквизит в шапке + табличная часть.

### Почему `requires-review` только при `breaking`

**Всегда:** шум. Исправление запятой — «требует ревью». Через месяц
100 флагов, все игнорируют.

**Только `breaking`:** флаг означает «смысл изменился, проверьте».
Это ценно. `fix` и `initial` не ставят флаг — они не меняют смысл.

### Почему агрегировать массовое обновление

**50 флагов:** шум. Не видно, что важно.

**Один список `kb_updates_pending`:** обзор. Видно, сколько и какие
(`breaking` vs `additive`). Пользователь разбирает пакетом.

### Почему архивные проекты не трогаем

**Трогаем:** засоряем `meta.yaml` флагами для закрытых проектов.
Никто не смотрит.

**Не трогаем:** чисто. Если клиент вернётся — проверим при переводе
в `active`.

### Почему `updates_kb` только активные

**Все:** `meta.yaml` превращается в журнал предложений. Раздувается.

**Только активные:** `meta.yaml` — карточка. История отклонённых —
в git log.

## 5. Что отвергли (альтернативы)

| Альтернатива ↕▾ | Почему отвергли ↕▾ |
|---|---|
| −Только `meta.yaml` (без frontmatter) | Не видно, какой артефакт на что ссылается |
| Только `frontmatter` (без `meta.yaml`) | Не видно «ключевых» ссылок проекта |
| Отдельный `kb-links.md` | Дубль `meta.yaml` + frontmatter |
| `requires-review` при любом обновлении | Шум, обесценивание флага |
| 50 отдельных флагов при массовом обновлении | Шум, не видно обзора |
| Трогать архивные проекты | Засорение `meta.yaml` |
| Хранить отклонённые `updates_kb` | Раздувание `meta.yaml` |
| Удалять KB-файл | Ломает ссылки |
⚙

## 6. Стресс-тест (edge cases)

### E1. KB-файл обновился с `fix`

**Поведение:** `requires-review` **не ставится**. Проект не трогаем.

### E2. KB-файл обновился с `breaking`

**Поведение:** `requires-review` ставится. Запись в `kb_updates_pending`.

### E3. KB-файл обновился, проект `archived`

**Поведение:** не трогаем. При переводе в `active` — проверим.

### E4. KB-файл помечен `deprecated`, проект `archived`

**Поведение:** предупреждение при следующем открытии (битая ссылка).

### E5. 10 KB-файлов обновились, 5 проектов ссылаются

**Поведение:** у каждого проекта — `kb_updates_pending` со списком.
Не 50 отдельных флагов.

### E6. Проект ссылается на несуществующий KB-файл

**Поведение:** M7-full при открытии проекта показывает предупреждение.
M8 (когда появится) — ловит.

### E7. KB-файл переименован (slug не изменился)

**Поведение:** ссылка работает. Ничего не делаем.

### E8. KB-файл переименован (slug изменился)

**Поведение:** M8 ловит битую ссылку. Пока M8 нет — предупреждение
при открытии.

### E9. Артефакт `approved`, KB обновился с `breaking`

**Поведение:** статус остаётся `approved`, добавляется `requires-review`.
Пользователь решает: обновить, перегенерировать или оставить.

### E10. Проект использует несколько конфигураций

**Поведение:** `kb_links` может содержать ссылки на разные конфигурации
(`unf/sales/reference`, `zup/salary/reference`). Всё работает.

### E11. M13 предлагает `updates_kb`, внедренец отклоняет

**Поведение:** запись не создаётся в `updates_kb`. История — в git log
(если было закоммичено) или нигде (если не было).

### E12. KB-файл обновился, но проект на него не ссылается

**Поведение:** проект не трогаем. Обновление KB не влияет.

## 8. Связанные механизмы

- **M1 (адресация):** ссылки по slug. Переименование не ломает.
- **M2 (связи):** внутри KB. M10 — между уровнями.
- **M3 (версии):** `change_type` определяет, ставить ли `requires-review`.
- **M7-full (маршрутизация):** использует `kb_links` для поиска.
Проверяет битые ссылки при открытии проекта.
- **M8 (валидация, отложен):** проверяет `related_kb`, `kb_links`,
индекс.
- **M9 (структура проекта):** `kb_links` в `meta.yaml`, `related_kb`
в frontmatter.
- **M12 (changelog):** триггер для `requires-review`.
- **M13 (генерация):** использует `kb_links` и `related_kb`. Предлагает
`updates_kb`.
- **M16 (кросс-проектный):** использует `_indexes/kb-usage.yaml`.

### 3.2. meta.yaml — карточка проекта

```yaml
# meta.yaml — карточка проекта
```

**Что важно:**

- `stage` — текущий этап (для дашборда и M9-навигации).
- `conditional_artifacts` — какие условные артефакты применимы.
- `health` — светофор для директора.
- `kb_links` — связь с KB (M10).

**Чего НЕТ:** бюджет, маржинальность, риски-каунтер. Это вычисляется
из артефактов (M16/M17), не хранится в meta.yaml. Иначе meta.yaml
станет «второй бухгалтерией», которую нужно синхронизировать.

### 3.3. project_id

**Правило:** slug из названия клиента (`aquaservice`, `romashka`).

**Если два проекта с одинаковым названием:** суффикс (`aquaservice-2`).

**Если клиент переименовался:** `project_id` **не меняется** (как «Код»
в 1С — стабильный идентификатор).

**Генерация:** при создании проекта (задача реализации M9). Пользователь
может переопределить, но по умолчанию — slug.

### 3.4. Версионирование артефактов проекта (гибрид — расширение M3)

**⚠️ Внимание:** это **расширение M3**, а не новое решение. См. ADR-022.

**M3 фиксировал:** «Проектные артефакты — другая модель: `status: draft →
approved → superseded`, без номеров версий».

**M9 расширяет:** для артефактов, которые **пересматриваются** (ТЗ,
требования, модель TO-BE), нужен и номер пересмотра (`vN`).

| Атрибут ↕▾ | Что означает ↕▾ | Пример ↕▾ |
|---|---|---|
| −`status` | Жизненный цикл документа | `draft` → `approved` → `superseded` |
| `version` | Номер значимого пересмотра | `1`, `2`, `3` |
⚙

**⚠️ Важно (уточнение):** `version: 1` в frontmatter = `v1` в тексте.
Это одно и то же. В YAML — число, в тексте — буква «v» для читаемости.
Не путать: `version: 1` не означает «первая версия из одной», а
«версия номер 1».

**Когда создаётся новая версия:**

- ТЗ утверждено (`approved`), клиент просит изменить → новая версия
(`version: 2`, в тексте `v2`), старая — `status: superseded`.
- Протокол встречи — **не версионируется** (это факт, а не документ).
- Чек-лист — **не версионируется** (можно перегенерировать).
- Заметки — **не версионируются** (это сырьё).

**Какие артефакты версионируются:**

| Версионируются (vN) ↕▾ | Не версионируются ↕▾ |
|---|---|
| −ТЗ на доработку (`tz-modifications.md`) | Протоколы встреч (`meetings/`) |
| Требования (`requirements.md`) | Чек-листы (`checklist.md`, `setup-checklist.md`) |
| Модель TO-BE (`to-be.md`) | Заметки (`notes.md`) |
| Карта соответствия (`mapping.md`) | Реестры (`registry-*`, `issues-log`) |
| Gap-анализ (`gap.md`) | Факты (`system-passport`) |
⚙

**Аналогия из 1С:** это как **«Версии объекта»** в справочнике. Каждая
версия имеет статус (актуальная / устаревшая) и номер. Оба атрибута.

### 3.5. Дашборд проекта

**Не хранится как файл.** Генерируется по запросу из `meta.yaml` +
артефактов.

**Что в дашборде:**

- Статус этапов (какие пройдены, какие в работе).
- Открытые риски (топ-5 из `registry-risks.md`).
- Открытые проблемы (из `issues-log.md`).
- Последние решения (из `registry-decisions.md`).
- Health (из `meta.yaml`).
- Ссылки на ключевые артефакты.

**Если нужен кэш:** `.cache/dashboard-{project_id}.md` (gitignored).

**Аналогия из 1С:** это как **«Пульс бизнеса»** — отчёт, а не документ.
Не хранится, строится по запросу.

### 3.6. Условные артефакты

**Отмечаются в `meta.yaml`:**

```
conditional_artifacts:
  migration: not_applicable     # миграции не было
  escalation: applicable        # крупный проект, эскалация нужна
  glossary: applicable          # богатая терминология
```

**Файл не создаётся, если `not_applicable`.** Если позже станет
`applicable` — файл создаётся при первом обращении.

**⚠️ Важно:** в шаблонах артефактов **НЕ ставить** `conditional: true`.
Условность — только в `meta.yaml`.

### 3.7. Архивация проекта

**Не переносить в `_archive/`.** Проект остаётся на месте,
`status: archived` в `meta.yaml`.

**M16/M17 по умолчанию не включают архивные проекты** (фильтр
`status != archived`). Если нужен архивный — явный фильтр.

**Аналогия из 1С:** это как **«Пометить на удаление»** — объект остаётся
в базе, но не участвует в работе.

### 3.8. Использование артефактов на других этапах

**Правило:** артефакт «живёт» в папке этапа, где создан, но может
**использоваться (быть прочитан)** на других этапах.

**Пример:** `stakeholders.md` создан на этапе 1 (`00_questionnaire/`),
но используется на этапе 3 для коммуникации. Он **не копируется** —
на него ссылаются через M10 или M7-full.

**Почему не копировать:** копия устареет. Ссылка — всегда актуальна.

**Аналогия из 1С:** это как **«Ввести на основании»** — новый документ
ссылается на старый, но не копирует его данные.

### 3.9. registry-decisions — где создаётся

**Создаётся на этапе 2** (первое проектное решение), но **живёт в корне**
(сквозной артефакт).

**Почему в корне:** он обновляется на всех этапах (этап 3, 4, 5).
Если бы он лежал в `01_design/`, при переходе на этап 3 пришлось бы
переносить.

**Аналогия из 1С:** это как **«Журнал документов»** — создаётся при
первом документе, но живёт отдельно от папок с документами.

### 3.10. Инициализация проекта

**M9 не описывает процесс инициализации** (кто создаёт `meta.yaml`,
как создаются папки). Это **задача реализации**.

**M9 определяет:**

- Что должно быть создано (структура + meta.yaml-шаблон).
- Где это лежит.
- Какие поля в meta.yaml.

**Реализация создаёт это при «новом проекте».** Как «Новый документ»
в 1С — пустая форма, которую заполняет пользователь.

### 3.11. Связь M9 ↔ M13

**M9 определяет структуру** (где что лежит). **M13 создаёт файлы**
в этой структуре.

M13 не решает «куда» — он использует шаблон структуры от M9.

**Аналогия из 1С:** «Справочник Номенклатура» (структура) и «Загрузка
данных» (создание элементов). Загрузка не решает, какие реквизиты —
она заполняет существующие.

## 4. Почему так (обоснование)

### Почему по этапам + сквозные в корне

**Альтернатива «только по этапам»:** сквозные артефакты (реестр рисков,
change log) непонятно куда. Они не принадлежат одному этапу.

**Альтернатива «только по типам»:** не видно, на каком этапе что
создаётся. Теряется контекст проекта.

**По этапам + сквозные:** видно и этап, и сквозные артефакты.
Как в 1С: документы — по журналам, а общие справочники — отдельно.

### Почему гибрид status + vN (расширение M3)

**M3 фиксировал только status:** практика показала, что для
пересматриваемых артефактов (ТЗ, требования) нужен и номер.

**M9 расширяет:** гибрид. Не отменяет M3, а дополняет.

**Почему не переписывать M3:** M3 уже fixed. Расширение — через ADR-022.

### Почему дашборд генерируется

**Альтернатива «отдельный файл»:** забыл обновить — устарел.

**Генерируется:** всегда актуален. Как отчёт в 1С.

### Почему условные артефакты в meta.yaml

**Альтернатива «файл с пометкой»:** лишний файл. Загрязняет структуру.

**Запись в meta.yaml:** компактно. Видно, что «мы проверили и решили,
что не нужно».

### Почему архивация через status, а не перенос

**Альтернатива «перенос в _archive/»:** ломает ссылки. M16/M17 должны
знать, где искать.

**status: archived:** ссылки работают, M16/M17 фильтруют по статусу.
Как «Пометка на удаление» в 1С.

### Почему артефакт не копируется на другой этап

**Альтернатива «копировать»:** копия устареет. Две версии одного факта.

**Ссылаться через M10/M7-full:** всегда актуально. Как «Ввести на
основании» в 1С.

## 5. Что отвергли (альтернативы)

| Альтернатива | Почему отвергли |
|---|---|
| Только по этапам (без сквозных в корне) | Сквозные артефакты непонятно куда |
| Только по типам | Не видно этапа |
| Только status (без vN) | Не видно, сколько раз пересматривали (M3 расширен) |
| Только vN (без status) | Не видно жизненного цикла |
| Дашборд — отдельный файл | Забыл обновить — устарел |
| Условные артефакты — файл с пометкой | Лишний файл |
| Архивация — перенос в `_archive/` | Ломает ссылки |
| meta.yaml с бюджетом и маржинальностью | «Вторая бухгалтерия», нужно синхронизировать |
| Копировать артефакт на другой этап | Копия устареет |
| M9 описывает инициализацию | Это задача реализации, не спецификации |

## 6. Стресс-тест (edge cases)

### E1. Проект закрыт

**Поведение:** `status: closed`, файлы остаются на месте, M16/M17
фильтруют.

### E2. Клиент вернулся через год

**Поведение:** `status: active`, stage восстанавливается из последнего
этапа.

### E3. Артефакт создан на этапе 1, нужен на этапе 3

**Поведение:** живёт в папке этапа 1, ссылка через M10 или M7-full.
**Не копируется.**

### E4. Условный артефакт стал применимым

**Поведение:** `conditional_artifacts.migration: applicable`, файл
создаётся при первом обращении.

### E5. Дашборд при отсутствии meta.yaml

**Поведение:** не генерируется, показывается «Проект не инициализирован».

### E6. Два проекта с одинаковым названием

**Поведение:** `project_id` с суффиксом (`aquaservice-2`).

### E7. KB-файл, на который ссылается проект, обновился

**Поведение:** M10 + M12: флаг `requires-review` в проекте.

### E8. Проект использует несколько конфигураций

**Поведение:** `meta.yaml: config: [unf, zup]`.

### E9. Артефакт approved, клиент просит изменения

**Поведение:** `status: superseded`, новый файл с `version: 2`.

### E10. Реестр проблем пуст

**Поведение:** файл `issues-log.md` не создаётся, пока нет первой
проблемы.

### E11. Проект удалён (не архивирован, а именно удалён)

**Поведение:** это **не штатная операция**. Проект не удаляется,
только архивируется (`status: archived`). Если нужно «удалить» —
это ручное решение с бэкапом.

### E12. Проект переименован (клиент сменил название)

**Поведение:** `project_id` не меняется, меняется `project_name` и
`client`. Ссылки работают.

### E13. Артефакт версионируется, но клиент не согласовал

**Поведение:** `status: draft`, `version: 2`. Клиент не согласовал —
v2 не становится `approved`.

### E14. Протокол встречи — нужна ли версия?

**Поведение:** **нет**. Протокол — это факт («что было сказано»).
Если встреча пересмотрена — новый протокол с новой датой.

## 8. Связанные механизмы

- **M1 (адресация):** проектные артефакты адресуются по пути
`01_projects/{project_id}/{этап}/{файл}`.
- **M2 (связи):** артефакты могут ссылаться друг на друга через `links`.
- **M3 (версии):** проектные артефакты — гибрид `status` + `vN`
(**расширение M3**, см. ADR-022).
- **M10 (связь с KB):** `meta.yaml` содержит `kb_links`.
- **M13 (генерация):** создаёт файлы в структуре M9.
- **M15 (Quick Capture):** заметки попадают в `00_questionnaire/notes.md`.
- **M16 (кросс-проектный):** использует `meta.yaml` + артефакты.
- **M17 (портфель):** использует `meta.yaml` (статус, health, stage).

```
                  ⚠️ version: 1 в frontmatter = v1 в тексте

                  НЕ для протоколов, чек-листов, заметок

Дашборд:          генерируется, не хранится (в памяти)

Условные:         conditional_artifacts: { migration: not_applicable }
                  ⚠️ В шаблонах НЕ ставить conditional: true

Архивация:        status: archived (не перенос в _archive/)

Инициализация:    задача реализации (не M9). M9 определяет «что»
```

Версионирование — расширение M3 (гибрид status + version).
**`version: 1` = `v1`** (уточнение). **Условность — только в meta.yaml,
не в шаблонах.**
