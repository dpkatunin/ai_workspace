# M7-full. Маршрутизация запросов агента

**Статус:** ✅ fixed
**Дата фиксации:** 2026-10-25
**Связанные:** M1 (адресация), M2 (связи), M3 (версии), M7-partial (противоречия), M11 (UX), M12 (changelog), M14 (качество)
**Дополняет:** M7-partial (противоречия KB vs кейс)

---

## 1. Контекст

**Какую задачу решаем.** Пользователь задаёт агенту вопрос на естественном
языке. Агент должен **понять, что спросили**, и **пойти в правильное место**
базы знаний. Без этого он будет искать «везде» и выдавать кашу.

**Ключевые требования (из UX):**
- **Не думать о структуре.** Пользователь не знает, где что лежит.
- **Точность.** Агент должен найти релевантное, а не всё подряд.
- **Честность.** Если ответа нет — сказать «нет», а не выдумывать.
- **Контекст.** Прямо релевантное — в ответ. Потенциально полезное —
  в конце как «кстати».

**Аналогия из 1С.** Это как **отбор в динамическом списке**. Вы открываете
список документов и ставите отбор: «только реализации», «только за этот
месяц», «только по этому клиенту». Без отбора — тысячи документов,
с отбором — 5 нужных. Агент делает то же самое: сначала отбор, потом поиск.

## 2. Решения (4 ключевых)

### 2.1. Семь типов запросов (+ `history`)

| № | Тип | Пример | Куда идёт |
|---|---|---|---|
| 1 | **Функционал** | «Как настроить ордерный склад?» | KB, `_configs/{config}/` |
| 2 | **Методология** | «Как проводить обследование?» | KB, `_universal/methodology/` |
| 3 | **Сравнение конфигураций** | «Чем УНФ отличается от ERP?» | KB, `_cross/` |
| 4 | **Кейсы** | «Покажи кейсы по складу» | KB, `_configs/{config}/cases/` |
| 5 | **Конкретный проект** | «Что решили у Ромашки?» | Projects, `01_projects/{id}/` |
| 6 | **Типовое vs проектное** | «Как в типовой vs как у клиента?» | Оба индекса |
| 7 | **История изменений** | «Что нового в 3.0.14?» | `_configs/{config}/_changelogs/` + `_versions/` |

**Почему `history` — отдельный тип:**
- Особый источник (`changelog` + `_versions/`, не основной KB-индекс).
- Особый формат ответа (diff «было → стало»).
- Особый фильтр (по версии конфигурации `config_version`).

**Почему `history` — ещё и модификатор:**
- «Как настроить биллинг» — функционал, история не нужна.
- «Что изменилось в настройке биллинга» — функционал + история.
  Если сделать `history` только отдельным типом, агент потеряет контекст
  «это про функционал».

**Модификатор `history` применим к:** функционал, сравнение конфигураций,
методология, кейсы, проект.

### 2.2. Гибридная классификация запроса

**Как работает:**
1. **Эвристика по ключевым словам** (быстро, дёшево).
   - «как настроить», «как работает» → функционал.
   - «как проводить», «этапы», «методология» → методология.
   - «сравни», «отличается», «vs» → сравнение конфигураций.
   - «покажи кейсы», «примеры внедрений» → кейсы.
   - «у клиента X», «в проекте Y» → конкретный проект.
   - «в типовой vs у клиента», «как у нас vs как правильно» → типовое vs проектное.
   - «что нового», «что изменилось», «в релизе» → история.
2. **Если эвристика уверена** (совпало ≥2 ключевых слова) — сразу
   применить тип.
3. **Если не уверена** (0–1 совпадение) — вызвать LLM для классификации.
4. **LLM возвращает** тип + уверенность (0–1). Если уверенность < 0.5 —
   спросить пользователя: «Это про функционал или про кейсы?»

**Аналогия из 1С:** это как **поиск контрагента** — сначала по ИНН
(быстро), если не нашли — по наименованию (средне), если не нашли —
по «похожим» (медленно, но находит). 90% вопросов — очевидные, 10% —
сложные.

**Почему не всегда LLM:** 40 вопросов × вызов LLM = дорого и медленно.
Гибрид даёт скорость для очевидного и точность для сложного.

### 2.3. Что делать, если 0 результатов (комбинация «честно + близкое + шире»)

**Алгоритм:**
1. **Честно сказать «точного нет»:** «В базе нет кейсов по ОС и НМА в УНФ».
2. **Сразу показать «близкое»:** «Но есть материалы по ОС в справочнике
   `unf/fixed-assets/reference` и кейс по основным средствам в проекте
   `romashka`».
3. **Спросить: «Поискать шире?»** — «Убрать фильтр "кейсы" и искать любые
   материалы по ОС?»

**Аналогия из 1С:** это как **отчёт «Остатки товаров»** — сначала
показывает «нет данных» (если фильтр слишком узкий), но предлагает
«показать все склады?».

**Почему не просто «нет»:** пользователь уйдёт ни с чем, хотя информация
может быть. Почему не просто «вот близкое»: пользователь может не понять,
что это не то, что он просил.

### 2.4. Связи в ответе (прямо релевантное + потенциально полезное)

**Алгоритм:**
1. **Основной поиск** — находит файл по типу запроса и фильтрам.
2. **Прямые связи (глубина 1)** — включаются в контекст ответа.
   Пример: нашли `unf/billing/reference`, видим `uses → unf/sales/reference`.
   `unf/sales/reference` **включается** в контекст (агент читает его
   и учитывает при ответе).
3. **Связи глубины 2** — **упоминаются** в конце ответа как «кстати».
   Пример: `unf/sales/reference` имеет `related → unf/pricing/reference`.
   Агент **не читает** `unf/pricing/reference`, но пишет в конце:
   «Кстати, это связано с ценообразованием — если нужно, расскажу».

**Аналогия из 1С:** это как **отчёт «Прибыли и убытки»** — основное видно
сразу (глубина 1), детали — по клику (глубина 2).

**Почему не всё в контекст:** ответ «распухнет», точность упадёт.
Почему не только упоминать: не хватит контекста для полного ответа.

## 3. Полная схема маршрутизации

```

Запрос пользователя
↓
[1] Классификация типа (эвристика → LLM, если не уверена)
↓
[2] Выбор индекса (KB / Projects / оба)
↓
[3] Применение фильтров (config, type, status, concept)
↓
[4] Основной поиск (RAG по индексу с фильтрами)
↓
[5] Если 0 результатов → «честно + близкое + шире»
↓
[6] Прямые связи (глубина 1) → в контекст
↓
[7] Проверка противоречий (M7-partial)
↓
[8] Проверка версий (M3: только актуальная, если не history)
↓
[9] Проверка качества (M14: файл requires-review → предупреждение)
↓
[10] Формирование ответа:

- основной ответ (из KB / Projects / оба)
- источники (slug + цитата)
- контекст (KB vs Project, если оба)
- «кстати» (связи глубины 2)
- предупреждения (requires-review, outdated, hallucination_link)

```

## 4. Выбор индекса (KB vs Projects)

| Тип запроса | Индекс | Фильтр |
|---|---|---|
| Функционал | KB | `config`, `type: reference/practical/objects` |
| Методология | KB | `config: universal` |
| Сравнение конфигураций | KB | `_cross/` + `concept` |
| Кейсы | KB | `type: case` + `concept` |
| Конкретный проект | Projects | `project_id` |
| Типовое vs проектное | **Оба** | KB: `config`, Projects: `project_id` |
| История | KB (changelogs) + `_versions/` | `config`, `config_version` |

**Как агент понимает, что нужен оба индекса:**
- Тип = «типовое vs проектное» → оба всегда.
- Тип = «конкретный проект» + в запросе «vs типовая» → оба.
- Тип = «функционал» + в запросе упомянут клиент («у Ромашки») → оба
  (KB для типового + Projects для клиента).

**Если проект не назван:** «Что мы решили по НДС» — тип не «конкретный
проект» (нет имени), а «функционал». Агент ищет в KB. Если пользователь
хочет по проекту — уточнит: «по какому проекту?»

## 5. Фильтры

### Автоматические (применяются всегда)

| Фильтр | Когда | Значение |
|---|---|---|
| `status: actual` | Всегда | Не цитировать `deprecated` (кроме `history`) |
| `config` | Если в запросе явно «УНФ» / «ERP» | `unf` / `erp` |
| `type` | По типу запроса | «как настроить» → `reference` + `practical` |
| `concept` | Если запрос про concept | «склад» → `concept: warehouse` |
| `level` | По типу запроса | «конкретный проект» → `project` |

### Явные (пользователь может указать)

- «покажи только кейсы» → `type: case`.
- «только по УНФ» → `config: unf`.
- «только актуальное» → `status: actual` (по умолчанию).
- «покажи и устаревшее» → `status: actual + deprecated`.

### Если фильтр слишком узкий

См. раздел 2.3 — «честно + близкое + шире».

## 6. Использование версий (M3)

**Правило:** по умолчанию — **только актуальная версия**. История —
по явному запросу.

| Ситуация | Что делает агент |
|---|---|
| «Как настроить биллинг» | Только актуальная v2. `changelog` — не показывается (если не спросят) |
| «Что изменилось в биллинге» | Актуальная v2 + `changelog` (diff «было → стало») |
| «Покажи, как было в v1» | Tool call `read_version` → `_versions/unf/billing/reference/v1.md` |
| Тип = `history` | `_configs/{config}/_changelogs/` + `_versions/` |

**Версия проекта (M12):** если проект имеет `config_version: "3.0.12"`,
а файл `applicable_from: "3.0.14"` — агент предупреждает:
«Этот файл описывает функционал с 3.0.14, у вас 3.0.12 — этого нет».

## 7. Противоречия (M7-partial)

**Встроены в маршрутизацию на шаге [7].** Правило из M7-partial:
- Агент **сначала** проверяет, есть ли противоречие между найденными
  фрагментами.
- Если есть — **классифицирует** тип (устаревание / частный случай /
  доработка / разный контекст / настоящее).
- **Потом** формирует ответ по правилу для этого типа:
  - устаревание → **выбор** (changelog > кейс > KB);
  - остальные → **объяснение** (показать оба, объяснить разницу).

**Почему не «сначала ответ, потом примечание»:** пользователь может
прочитать ответ и не заметить примечание. Противоречие — это важная
информация, она должна быть **в основном ответе**, а не в сноске.

## 8. Формат ответа

### Обязательные элементы

1. **Основной ответ** — по существу вопроса.
2. **Источники** — slug + цитата (для проверки).
3. **Контекст** — если ответ из обоих индексов, маркировать:
   «В типовой (KB): … У клиента X (проект): …»
4. **«Кстати»** — связи глубины 2 (если есть).
5. **Предупреждения** — `requires-review`, `outdated`, `hallucination_link`.

### Шаблон

```markdown
[Основной ответ]

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
**Источники:**
- KB: `unf/sales/practical` — «[цитата]»
- KB: `unf/sales/reference` — «[цитата]»

**Контекст:** [если ответ из обоих]
- В типовой: [фрагмент]
- У клиента X: [фрагмент]

**Кстати:** это связано с `unf/pricing/reference` (ценообразование).
Если нужно — расскажу подробнее.

**⚠️ Предупреждения:**
- Файл `unf/sales/reference` помечен `requires-review` (затронут релизом 3.0.14).
- Файл `unf/sales/practical` недавно обновлён (v2).
```

### Если ответа нет (0 результатов)

```
Точных кейсов по ОС и НМА в УНФ **нет**.

Но есть близкое:
- `unf/fixed-assets/reference` — материалы по ОС в справочнике
- `01_projects/romashka/...` — кейс по основным средствам у Ромашки

[Поискать шире — любые материалы по ОС?]  [Уточнить запрос]
```

что все slug в ответе существуют в `_indexes/edges.yaml` или в файловой
системе. Если нет — **не включает** ссылку в ответ, пишет в feedback.

## 10. Почему так (обоснование)

### Почему 7 типов, а не 6

**Альтернатива «6 типов»:** «что нового в релизе» не покрывается.
Агент ищет в обычных файлах, не находит, выдаёт «в базе нет», хотя
changelog есть.

**7-й тип:** особый источник, особый формат. Логично.

### Почему гибрид, а не всегда LLM

**Всегда LLM:** 40 вопросов × вызов = дорого и медленно. Не нужно
для очевидного.

**Всегда эвристика:** не ловит нестандартные формулировки.

**Гибрид:** быстро для 90%, точно для 10%.

### Почему «честно + близкое + шире», а не просто «нет»

**Просто «нет»:** пользователь уйдёт ни с чем, хотя информация может быть.

**Просто «близкое»:** пользователь может не понять, что это не то.

**Комбинация:** честность + полезность + контроль.

### Почему «прямо релевантное + потенциально полезное»

**Всё в контекст:** ответ «распухает», точность падает.

**Только упоминать:** не хватит контекста для полного ответа.

**Прямо релевантное — в ответ, глубина 2 — в «кстати»:** баланс.

## 12. Стресс-тест (edge cases)

### E1. Запрос с двумя типами

**Сценарий:** «Что нового в настройке биллинга в 3.0.14?»
**Поведение:** тип = `функционал`, модификатор = `history`. Агент ищет
в `unf/billing/reference` + `unf/_changelogs/3.0.13→3.0.14`. Отвечает:
«настройка такая-то, в 3.0.14 добавилось то-то».

### E2. Запрос без явного типа

**Сценарий:** «Склад».
**Поведение:** эвристика не уверена (1 слово). LLM: «это функционал
или кейсы?» Если LLM не уверен — спросить пользователя: «Про функционал
склада или про кейсы?»

### E3. Запрос на проект, которого нет

**Сценарий:** «Что решили у Иванова?» — проекта `ivanov` нет.
**Поведение:** «Проект `ivanov` не найден. Есть проекты: `romashka`,
`aquaservice`. Уточните?»

### E4. Запрос про концепт, которого нет в KB

**Сценарий:** «Как настроить ОС и НМА?» — раздела `fixed-assets` нет.
**Поведение:** «Раздела ОС и НМА в базе нет. Есть близкое: … Поискать
шире?»

### E5. Запрос про историю, а changelog нет

**Сценарий:** «Что изменилось в 3.0.15?» — changelog 3.0.14→3.0.15 нет.
**Поведение:** «Changelog 3.0.15 не найден. Последний доступный: 3.0.14.
Хотите посмотреть его?»

### E6. Фильтр слишком узкий

**Сценарий:** «Покажи кейсы по ОС и НМА в УНФ» — кейсов по ОС нет.
**Поведение:** см. 2.3 — «честно + близкое + шире».

### E7. Ответ из обоих индексов с противоречием

**Сценарий:** «Как настроить склад у Ромашки?» — KB говорит одно,
проект другое.
**Поведение:** M7-partial, тип «разный контекст» (или «настоящее
противоречие»). Ответ: «В типовой: … У Ромашки: … Разница: …».

### E8. Ссылка на slug, которого нет

**Сценарий:** агент собрал ответ, но один из slug не существует.
**Поведение:** пост-проверка (шаг 9). Slug **не включается** в ответ,
feedback-запись `hallucination_link`.

### E9. LLM не уверен в классификации

**Сценарий:** эвристика не уверена, LLM вернул confidence 0.4.
**Поведение:** спросить пользователя: «Уточните — это про функционал,
кейсы или проект?»

### E10. Запрос на сравнение, но cross-файла нет

**Сценарий:** «Чем производство в УНФ отличается от ERP?» — cross-файла
нет.
**Поведение:** «Cross-файла нет. Но есть `unf/production/reference`
и `erp/production/reference` — могу сравнить по ним. Хотите?»

### E11. Связь глубины 2 указывает на несуществующий файл

**Сценарий:** в «кстати» агент хочет упомянуть `unf/pricing/reference`,
а его нет.
**Поведение:** не упоминать. Feedback-запись `hallucination_link`.

### E12. Запрос на `history` без указания версии

**Сценарий:** «Что изменилось в биллинге?» — без версии.
**Поведение:** «Последний changelog: 3.0.13→3.0.14. Показать его?
Или уточните версию».

| −1 | Точный промпт для LLM-классификации типа запроса | При реализации |

## 14. Связанные механизмы

- **M1 (адресация):** все ссылки в ответе — slug.
- **M2 (связи):** глубина 1 в контекст, глубина 2 в «кстати».
- **M3 (версии):** по умолчанию актуальная, история по запросу.

- **M12 (changelog):** источник для типа `history`.
- **M14 (качество):** пост-проверка slug, предупреждения, feedback-записи.

## ADR-012. Маршрутизация запросов (M7-full)

**Дата:** 2026-10-25
**Статус:** accepted

**Контекст:** как агент понимает, что спросили, и куда идти.

**Решение:** четыре ключевых решения.

### 1. Семь типов запросов (+ `history`)

| № ↕▾ | Тип ↕▾ | Куда ↕▾ |
|---|---|---|
| −1 | Функционал | KB, `_configs/{config}/` |
| 2 | Методология | KB, `_universal/methodology/` |
| 3 | Сравнение конфигураций | KB, `_cross/` |
| 4 | Кейсы | KB, `_configs/{config}/cases/` |
| 5 | Конкретный проект | Projects |
| 6 | Типовое vs проектное | Оба индекса |
| 7 | История | `_changelogs/` + `_versions/` |
⚙

`history` — ещё и модификатор к другим типам (функционал + history,
сравнение + history и т.д.).

### 2. Гибридная классификация

Эвристика по ключевым словам → если уверена (≥2 совпадений) — применить.
Если не уверена — LLM. Если LLM не уверен (<0.5) — спросить пользователя.

### 3. При 0 результатов — «честно + близкое + шире»

1. Честно: «точного нет».
2. Близкое: «вот что есть».
3. Спросить: «поискать шире?»

### 4. Связи в ответе — глубина 1 в контекст, глубина 2 в «кстати»

Прямые связи (глубина 1) — включаются в контекст ответа.
Связи глубины 2 — упоминаются в конце как «кстати».

**Почему так:**

- 7 типов: «что нового в релизе» не покрывается 6 типами.
- Гибрид: 90% вопросов очевидны, 10% — сложные. Гибрид даёт скорость + точность.
- «Честно + близкое + шире»: честность + полезность + контроль.
- «Глубина 1 в контекст + глубина 2 в кстати»: баланс.

**Альтернативы:**

- 6 типов (без history) — отвергнуто.
- Всегда LLM — отвергнуто: дорого.
- Всегда эвристика — отвергнуто: не ловит нестандартные.
- Просто «нет» при 0 результатов — отвергнуто: пользователь уйдёт ни с чем.
- Всё в контекст — отвергнуто: ответ «распухает».
- Не использовать связи — отвергнуто: пользователь не знает, что они есть.

**Следствия:** пост-проверка slug (M14), предупреждения (requires-review,
outdated), feedback-записи.
