## 2. `M9_project_structure.md` → v2

### 2.1. Новый раздел «Несколько конфигураций»

**Действие:** добавить раздел после раздела про `meta.yaml`, перед разделом про этапы.

```
### Несколько конфигураций

Проект может охватывать **несколько конфигураций 1С** одновременно (типовой случай: «УНФ + ЗУП» на одном клиенте, где зарплата вынесена отдельно).

**Объявление в `meta.yaml`** — всегда список:

```yaml
config:
  - unf
  - zup
```

Даже если конфигурация одна — список:

```
config:
  - unf
```

**Отображение имени.** Поле `{{CONFIG_NAME}}` в шаблонах резолвится из `config_registry.yaml`:

- Для каждой конфигурации в списке берётся её `merge_name`.
- Результат — конкатенация через `" + "` в порядке, в котором конфигурации перечислены в `meta.yaml`.

**Примеры:**

| `config` в meta.yaml ↕▾ | `{{CONFIG_NAME}}` ↕▾ |
|---|---|
| −`[unf]` | `УНФ 3.0` |
| −`[zup]` | `ЗУП 3.1` |
| −`[unf, zup]` | `УНФ 3.0 + ЗУП 3.1` |
| −`[zup, unf]` | `ЗУП 3.1 + УНФ 3.0` |
⚙

**Порядок — из `meta.yaml`, не из реестра.** Если в проекте важно, чтобы «УНФ» шла первой — так и пишется в списке. Это детерминированно для файла и соответствует тому, как пользователь перечисляет конфигурации.

**Обязательность `merge_name`.** В `config_registry.yaml` поле `merge_name` обязательно для каждой конфигурации. Если его нет — ошибка при загрузке реестра (не fallback на `short`). Это защищает от «тихого» расхождения имён в документах.

**Валидация при загрузке `meta.yaml`:**

1. Каждый `id` из `config` должен присутствовать в `config_registry.yaml`. Если `id` не найден — ошибка: «Конфигурация `{id}` не найдена в `config_registry.yaml`. Добавьте её в реестр».
2. У каждой найденной конфигурации должен быть `merge_name`. Если нет — ошибка: «У конфигурации `{id}` отсутствует `merge_name` в `config_registry.yaml`».
3. `config` не может быть пустым списком. Пусто — ошибка: «Поле `config` обязательно. Укажите хотя бы одну конфигурацию».
4. Дубликаты в `config` — ошибка: «Дубликат конфигурации `{id}` в `meta.yaml`».

**Никакого fallback на `id` или `short`.** Иначе `{{CONFIG_NAME}}` в документе будет «erp» вместо «ERP 2.5» — тихое расхождение, которое найдётся через полгода на защите проекта у клиента.

**Не нормализуем дубликаты (не дедуплицируем).** Причины:

- Дедупликация скрывает ошибку ввода. Если пользователь дважды написал `unf`, это сигнал: либо копипаст, либо непонимание структуры.
- Тихая нормализация создаёт прецедент: «а что ещё ты молча исправишь?».
- Стоимость явной ошибки — 5 секунд на исправление `meta.yaml`. Стоимость скрытой нормализации — неопределённость при отладке через месяц.

*Аналогия из 1С:* `{{CONFIG_NAME}}` — это как `Представление()` объекта; `merge_name` — это реквизит «Наименование для печати», который задаётся в справочнике, а не собирается на лету.

```
