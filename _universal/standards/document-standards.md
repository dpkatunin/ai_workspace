# Стандарты оформления документов

> **Что это:** правила, как оформлять проектные документы. Применимо
> ко всем артефактам (и созданным вручную, и сгенерированным M13).
>
> **Зачем:** чтобы документы были единообразными. Клиент не должен
> привыкать к разному стилю у разных внедренцев.
>
> **Аналогия из 1С:** это как **«Учётная политика»** — правила, по которым
> работает вся практика. Не рекомендации, а стандарт.
>
> **Исправлено:** 2026-10-25 (добавлен раздел про битые ссылки)

---

## 1. Структура документа

Каждый проектный документ (кроме протоколов встреч) должен содержать:

```

1. Заголовок (H1)
2. Краткое резюме (1–3 предложения)
3. Основная часть (разделы H2)
4. Источники (KB-ссылки)
5. Метаданные (frontmatter)

```

**Исключение:** протоколы встреч — только дата, участники, решения,
задачи. Без резюме и источников.

---

## 2. Заголовок (H1)

**Правило:** один H1 на документ. Соответствует названию артефакта.

**Плохо:**
```markdown
# Карта
# соответствия
```

**Хорошо:**

```
# Карта соответствия: ООО «АкваСервис»
```

---

## 3. Краткое резюме

**Правило:** 1–3 предложения. Что это за документ, для кого, что внутри.

**Плохо:**

```
## Резюме
Этот документ содержит карту соответствия. В нём описаны процессы
клиента и их сопоставление с модулями УНФ. Документ подготовлен
аналитиком на основе обследования.
```

**Хорошо:**

```
## Резюме
Карта соответствия процессов ООО «АкваСервис» модулям УНФ 3.0.
Покрыто штатно: 12 процессов. Требуют доработки: 3. Не покрыто: 1.
```

---

## 4. Таблицы

**Правило:** таблицы — для структурированных данных (списки, сравнения).
Не для прозы.

**Плохо:**

```
| Текст |
|---|
| Процесс продажи покрывается штатно через заказ покупателя и расходную накладную. |
```

**Хорошо:**

```
| Процесс | Модуль | Покрытие | Источник KB |
|---|---|---|---|
| Продажа | Продажи | Штатно | `unf/sales/reference` |
```

---

## 5. Ссылки на KB

**Правило:** каждая ссылка на KB — в формате `slug` (M1). Не «см. файл
05_Склад», а «см. `unf/warehouse/reference`».

**В тексте:** в скобках после утверждения.

**В frontmatter:** в поле `related_kb` (M10).

**Плохо:**

```
Склад настраивается через ордерную схему (см. файл про склад).
```

**Хорошо:**

```
Склад настраивается через ордерную схему
(см. `unf/warehouse/reference`).
```

---

## 6. Метаданные (frontmatter)

**Правило:** каждый артефакт имеет YAML frontmatter. Минимум:

```
---
title: "Карта соответствия: ООО «АкваСервис»"
type: artifact
artifact_type: mapping
project_id: aquaservice
stage: 01_design
status: draft          # draft | approved | superseded
version: 1             # ⚠️ version: 1 = v1 в тексте
created: 2026-10-25
updated: 2026-10-25
related_kb:
  - unf/sales/reference
---
```

**Для протоколов встреч** — дополнительно `meeting_date`, `participants`.

**⚠️ Важно:** `version: 1` в frontmatter = `v1` в тексте. Это одно
и то же. В YAML — число, в тексте — буква «v» для читаемости.

---

## 7. Статусы

| Статус ↕▾ | Что означает ↕▾ |
|---|---|
| −`draft` | Черновик, не согласован |
| `approved` | Согласован с клиентом/руководителем |
| `superseded` | Заменён новой версией |
⚙

**Правило:** документ не может быть `approved`, пока не прошёл ревью.

---

## 8. Версионирование (M9, ADR-022)

**Правило:** `version: N` создаётся при **значимом** пересмотре.
Опечатки и мелкие правки — без новой версии.

**Когда создаётся `version: 2`:**

- ТЗ утверждено, клиент просит изменить.
- Модель TO-BE пересмотрена после нового обследования.
- Требования изменились.

**Когда НЕ создаётся:**

- Исправлена опечатка.
- Переформулирован абзац без изменения смысла.

**⚠️ Уточнение:** `version: 1` = `v1`, `version: 2` = `v2`. Число в YAML,
буква «v» — в тексте. Это одно и то же.

---

## 9. Битые ссылки (добавлено 2026-10-25)

**Правило:** если ссылка на KB не работает — это ошибка, которую надо
исправить до сдачи документа.

**Причины битой ссылки:**

- KB-файл переименован (slug изменился).
- KB-файл помечен `deprecated` (устарел).
- Опечатка в slug.
- KB-файл ещё не создан (ссылка на будущее — запрещена).

**Что делать:**

1. Проверить, существует ли slug (M8, когда появится).
2. Если KB-файл переименован — заменить slug на новый.
3. Если KB-файл `deprecated` — заменить на актуальный.
4. Если опечатка — исправить.

**Чек-лист перед сдачей:**

- □  
Все `related_kb` в frontmatter существуют в KB.
- □  
Все ссылки в тексте (`\`unf/...``) существуют в KB.
- □  
Нет ссылок на `deprecated`-файлы (или есть пометка «устарело»).

**Аналогия из 1С:** это как **«Проверка ведения учёта»** — битые ссылки
это ошибка, которую надо исправить. Не «потом», а до сдачи.

---

## 10. Язык и стиль

**Правило:** деловой, без «воды». Не «осуществить», а «сделать».
Не «в целях осуществления», а «чтобы».

**Плохо:**

```
В целях осуществления оптимизации бизнес-процессов необходимо
произвести настройку модуля «Склад».
```

**Хорошо:**

```
Настроить модуль «Склад»: включить ордерную схему, создать склады.
```

---

## 11. Чек-лист перед сдачей документа

- □  
Один H1, соответствует названию.
- □  
Есть краткое резюме (1–3 предложения).
- □  
Таблицы для структурированных данных.
- □  
Ссылки на KB в формате slug.
- □  
Все ссылки на KB существуют (нет битых).
- □  
Frontmatter заполнен.
- □  
Статус `draft` (или `approved`, если прошёл ревью).
- □  
Нет «воды» и канцелярита.
- □  
Нет опечаток (проверить).

# Стандарты коммуникации с клиентом

> **Что это:** правила, как общаться с клиентом в проекте. Применимо
> ко всем ролям (аналитик, внедренец, РП).
>
> **Зачем:** чтобы клиент получал единый опыт. Не «один внедренец пишет
> длинно, другой — коротко». Стандарт — для всех.
>
> **Аналогия из 1С:** это как **«Регламент обмена данными»** — правила,
> по которым система общается с внешним миром. Только для людей.
>
> **Исправлено:** 2026-10-25 (добавлен раздел про эскалацию)

---

## 1. Принципы общения

| Принцип | Что значит |
|---|---|
| **Краткость** | Не «в целях осуществления», а «чтобы». Клиент занят |
| **Конкретность** | Не «надо настроить склад», а «включить ордерную схему на складе №1» |
| **Честность** | Если не знаем — «уточню», а не выдумываем |
| **Структура** | Списки, таблицы, а не «поток сознания» |
| **Сроки** | Если обещали — сделали. Если не успеваем — предупредили заранее |

---

## 2. Формат ответа на вопрос клиента

**Правило:** ответ на вопрос — в три шага.

1. **Прямой ответ** (1–2 предложения).
2. **Детали** (если нужно — список, таблица).
3. **Что дальше** (что клиенту сделать, что мы сделаем).

**Пример:**

> **Вопрос:** Можно ли в УНФ вести несколько организаций в одной базе?
>
> **Ответ:** Да, можно.
>
> **Детали:**
> - Включить опцию «Несколько организаций» в настройках.
> - Создать карточки организаций.
> - В документах выбирать организацию.
>
> **Что дальше:** Мы настроим это на этапе 3. Вам нужно будет предоставить
> реквизиты второй организации.

---

## 3. Формат плохих новостей

**Правило:** плохие новости — сразу, с вариантами решения.

**Плохо:**
> «Мы не успеваем к сроку.»

**Хорошо:**
> «Срок сдвигается на 3 дня. Причина: клиент не предоставил доступ к базе
> вовремя. Варианты:
> 1. Сдвинуть запуск на 3 дня.
> 2. Запустить без модуля X, добавить его позже.
> 3. Ускорить за счёт дополнительных ресурсов (потребует бюджета).
>
> Рекомендуем вариант 1.»

---

## 4. Формат отчёта о статусе

**Правило:** статус — в три блока.

```markdown
## Статус проекта «АкваСервис» на 25.10.2026

### Сделано
- Настроен склад (ордерная схема).
- Настроены виды цен.

### В работе
- Настройка продаж (в процессе).

### Требует решения
- Клиент не предоставил доступ к базе для миграции. Срок: до 27.10.

**Правило:** не больше 5 пунктов в каждом блоке. Если больше — детали
в отдельном документе.

---

## 5. Формат протокола встречи

**Правило:** протокол — в четыре блока.

```
## Протокол встречи от 25.10.2026

**Участники:** Иванов (клиент), Петров (внедренец).

### Обсудили
- Настройка склада: решили использовать ордерную схему.
- Миграция: клиент предоставит данные до 27.10.

### Решили
- Склад — ордерный, ячейки не используем.
- Миграция — 27.10, отвественный: Иванов.

### Задачи
- [ ] Петров: настроить ордерную схему (до 26.10).
- [ ] Иванов: предоставить данные для миграции (до 27.10).
```

---

## 6. Что НЕ делать в общении с клиентом

| Не делать ↕▾ | Почему ↕▾ |
|---|---|
| −Обещать без проверки | Не сможем выполнить — потеряем доверие |
| Скрывать проблемы | Клиент узнает позже — будет хуже |
| Использовать жаргон | Клиент не поймёт |
| Писать длинно | Клиент не дочитает |
| Обсуждать коллег | Непрофессионально |
⚙

---

## 7. Формат вопросов клиенту

**Правило:** вопрос — конкретный, с вариантами ответа (если возможно).

**Плохо:**

> «Как вы хотите настроить склад?»

**Хорошо:**

> «Какой тип склада вам нужен?
> 
> 1. Обычный (без ордеров) — проще, но меньше контроля.
> 2. Ордерный (с приёмкой/отгрузкой через кладовщика) — больше контроля,
> но нужно обучение кладовщика.
> 
> Рекомендуем вариант 2, если у вас больше 100 операций в день.»

## 8. Эскалация (добавлено 2026-10-25)

**Правило:** если проблема выходит за рамки проекта — эскалировать
по цепочке. Не решать в одиночку.

**Когда эскалировать:**

- Клиент не платит.
- Конфликт с руководителем клиента.
- Проблема, которая может сорвать сроки.
- Техническая проблема, которую нельзя решить на месте.
- Изменение требований, которое влияет на бюджет.

**Как эскалировать:**

| Уровень | Кто | Когда |
|---|---|---|
| 1 | РП проекта | Первая проблема (сроки, ресурсы) |
| 2 | Директор практики | Проблема выходит за рамки проекта |
| 3 | Руководство компании | Юридические, финансовые риски |

**Формат эскалации:**

```
## Эскалация: [краткое описание]

**Проект:** {{PROJECT_NAME}}
**Дата:** {{DATE}}
**Уровень:** 1 / 2 / 3

### Проблема
Что случилось (факты, не эмоции).

### Влияние
- Сроки: сдвиг на X дней.
- Бюджет: дополнительные расходы Y.
- Клиент: риск потери / конфликт.

### Что уже сделали
- Попытка 1: …
- Попытка 2: …

### Что нужно от руководителя
- Решение: …
- Ресурсы: …
```

**Аналогия из 1С:** это как **«Уведомление»** в 1С — если проблема
не решается на месте, она идёт наверх. Не «героически решаем сами»,
а «эскалируем вовремя».

---

## 9. Чек-лист перед отправкой сообщения клиенту

- □  
Прямой ответ на вопрос (если вопрос был).
- □  
Конкретика (не «надо», а «что именно»).
- □  
Нет жаргона (или он объяснён).
- □  
Структура (список, таблица, а не поток).
- □  
Что дальше (что клиенту сделать).
- □  
Нет опечаток.
- □  
Если проблема — есть варианты решения.
- □  
Если эскалация — формат эскалации соблюдён.

решения (`registry-decisions`, `to-be`, `requirements`, `tz-modifications`).
Это создаёт человек.

## Связь с universal-слоем

Для каждого артефакта из списка M13 — есть шаблон в `_universal/templates/`.
Шаблон задаёт структуру, M13 заполняет данными проекта и KB.

**Аналогия из 1С:** шаблон — это **макет печатной формы**, M13 — это
**заполнение макета данными**. Без макета — нечего заполнять. Без данных —
пустой макет.
